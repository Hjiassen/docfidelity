# ADR-008 开源版即完整版，不做 Open Core

- 状态：Accepted
- 日期：2026-09-17
- 关联：需求 2.4；设计 DD-1.1、DD-20（风险 #11）

## 背景

Open Core（核心开源 + 关键能力闭源）是常见的商业化路径，但对本项目有一个
**致命的副作用**：

本项目的核心承诺是「样式层零改动」。这条承诺的可信度只能靠使用者**自行验证**——
跑一遍、比对产物、看门禁报告。如果关键能力（比如某种模板能力、某个渲染策略）
只存在于闭源版，使用者就无法自证承诺成立，只能选择相信。

而"只能相信"恰恰是这个产品最不该要求的。

## 决策

**开源版即完整版**。约束落在资产上：

> 每一个私有能力，都必须在自制示例模板中复现**同等配置**。

也就是说，能力项表（需求 10.10）中的每一项，都要在 `demo-templates/` 里有对应的、
可运行的自制示例。开源版不能退化为"几个固定模板的演示品"。

## 备选方案与取舍

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| Open Core | 有明确商业化路径 | 社区信任成本高；能力边界说不清；与"可自部署"定位冲突 | 否 |
| **完整开源（采纳）** | 定位清晰、可信；示例资产可自证能力 | 需要自造示例模板覆盖全部能力项，投入前置 | 采纳 |

## 后果

### 正面

- 「一键体验」成为可验证承诺：`docker compose up` 后用示例数据跑通；
- 使用者可以在自己的模板上独立复现，不必依赖厂商背书。

### 负面（明确接受的代价）

- 示例资产的建设是**前置投入**，且必须随能力项表同步维护；
- 短期内失去"闭源能力"这块筹码。

### 需要后续跟进

- 能力项表逐条对照检查纳入 P0 退出条件。
