# ADR-005 契约模块为依赖之根，OOXML 只在渲染与门禁层

- 状态：Accepted
- 日期：2026-09-17
- 关联：需求 4.1 决策五、4.6；设计 DD-1.1、DD-2.2、DD-2.3

## 背景

多个模块要并行开发时，"谁定义数据结构"必须先有答案。若各模块自带数据结构：

- 同一个概念（比如"样式"）会在多处定义，字段逐渐漂移；
- 模块之间需要写转换层，转换层本身成为 bug 来源；
- 契约无法冻结，四条并行开发线也就无从谈起。

另一条边界同样关键：**OOXML 原语的可见范围**。一旦 `compose` 能直接构造
`w:tblStylePr`，样式保真的边界就在代码层面失守了——而且是渐进的、不易察觉的失守。

## 决策

1. `contracts` **只依赖 `pydantic`**，被内核所有模块依赖，是依赖之根；
2. **OOXML 读写只有一个出口**（`ooxml` 模块），且只允许 `registry`（入库）/ `render` / `qa` 使用；
3. `compose` 与 `server/api` **明确禁止** import `ooxml`；
4. 契约冻结的边界定义为「**字段与语义**」：允许增加可选字段，修改已有字段的
   名称或语义属破坏性变更，须走 RFC。

2026-10-14：决策载荷、输出和适配器协议下沉到 `contracts`，规则路由、基线与留痕位于 `pipeline.decisioning`。`agents` 位于 pipeline 之上；服务端组合根通过发行入口点发现实现并注入协议实例。规则会话不加载 agents，pipeline 静态导入 agents 在 CI 被禁止。

## 备选方案与取舍

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 各模块自带数据结构 | 局部灵活，无先行成本 | 概念重复、转换成本、语义漂移；契约无法冻结 | 否 |
| **单一契约根（采纳）** | 契约可冻结、可导出 schema、可做兼容性测试；对外承诺唯一 | 契约层成为串行瓶颈，必须先冻结才能并行 | 采纳 |

## 后果

### 正面

- 四条并行开发线成立（契约冻结是唯一前置）；
- 契约可导出 JSON Schema 交付前端，前端不必手写重复类型；
- OOXML 的可见范围可被机器校验，样式保真边界不靠自觉。

### 负面（明确接受的代价）

- **契约层是最先必须完成的一环**，排期上不能延后；
- 契约变更需要同步 Schema 导出、兼容性测试与 CHANGELOG，流程偏重。

### 需要后续跟进

- `.importlinter` 中的六条契约（分层 + 四条禁止依赖 + server 侧）；
- 契约变更走 L3 流程（[GOVERNANCE.md](../../../GOVERNANCE.md) 第 4 节）。
