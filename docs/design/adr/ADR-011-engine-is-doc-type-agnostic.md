# ADR-011 引擎与文档类型无关

- 状态：Accepted
- 日期：2026-09-17
- 关联：需求 1.3、4.1 决策六、4.9、NFR-28/29、验收 42–45；设计 DD-2.3（2）

## 背景

如果把文档类型写进引擎——`if doc_type == "详细设计": ...`——会产生一个不可逆的
后果：**每接入一类新文档，都要改引擎代码**。

这条路的终点是清晰的：引擎里堆满针对各类型的特例，测试矩阵随类型数乘性增长，
开源版最终退化为"支持若干固定模板的演示品"。而本项目的定位恰恰是
**通用文档撰写引擎**。

## 决策

文档类型与领域概念**全部外置为数据**：

| 概念 | 载体 | 引擎的态度 |
| --- | --- | --- |
| 文档类型 | `DocTypeProfile`（YAML 档案） | 只读 `genre` / `projections` / `bindings`，不认识取值 |
| 领域模型 | `DomainModel`（YAML 声明） | 只按 `key` / `fields` / `comparable` / `traceable` 行事，不分支 `kind` |
| 门禁规则 | `RuleSet`（YAML） | 按声明加载执行 |
| 模板能力 | 模板包契约 | 只查契约 |

并设**机器门禁**：`src/docfidelity/**` 中禁用词（文档类型名 + 领域概念名 +
`kind` / `doc_type` 判别分支）命中数必须为 **0**（NFR-28 / 验收 42）。

## 备选方案与取舍

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 引擎内置类型支持 | 单类型接入快，可做深度优化 | 类型数增长后无法维护；通用性承诺不成立 | 否 |
| **类型完全外置（采纳）** | 通用性可验证（同源多型）；接入成本恒定 | 抽象层设计门槛高；需持续抵抗"加个分支"的诱惑 | 采纳 |

## 后果

### 正面

- 同一事实包可产出 ≥2 类文档（含 1 类非软件域）且**零代码接入**（验收 43–45）；
- 领域词汇的演进不触发引擎发版；
- 引擎的测试矩阵与文档类型数解耦。

### 负面（明确接受的代价）

- 抽象层必须一开始就设计对：投影 DSL 的表达能力若不足，会遇到"只能用分支解决"
  的压力，而此时加分支会让门禁变红——**这正是设计意图**；
- 档案的编写门槛上升，需要配套文档与校验（`E_PROFILE_INVALID`）。

### 需要后续跟进

- `scripts/check_forbidden_words.py` 与 `qa.type_agnostic` 共用同一份词表；
- 词表维护纪律：新增领域词汇时更新词表，而不是在引擎里加特例；
- 配套 AST 分支检查（`x.kind == "..."` / `x.doc_type == "..."`）已在内置检查中实现。
