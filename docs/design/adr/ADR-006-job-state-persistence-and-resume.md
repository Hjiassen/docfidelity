# ADR-006 作业与阶段状态持久化，按阶段续跑

- 状态：Accepted
- 日期：2026-09-17
- 关联：需求 4.8、6.7；设计 DD-1.1、DD-11、DD-11.3

## 背景

构建链路有五个阶段：`ingest → compose → render → refresh → qa`。其中 `render`
是最昂贵的一段（深拷贝 + 注入 + 分页 + 域刷新），大型文档可达数分钟。

两个现实约束：

- 用户会关掉页面、会重启服务、会以为卡住了；
- 若"重启 = 从头再来"，则 `render` 完成后在 `qa` 失败的那次构建，代价要被支付两遍。

## 决策

作业与阶段状态落库，三张表：

| 表 | 承载 |
| --- | --- |
| `jobs` | 作业（编排 / 子作业）与状态 |
| `stages` | 阶段状态、进度、错误 |
| `stage_checkpoints` | 阶段断点：输入摘要 + 输出逻辑名 → 路径 + **阶段实现版本** |

1. 阶段实现必须幂等；
2. `StageCheckpoint.version` 取 `STAGE_IMPL_VERSION`；**阶段实现变更即历史 checkpoint 失效**，
   强制重跑；
3. 作业状态迁移的**唯一入口**是 `JobStateMachine.apply`，任何代码不得直接
   `UPDATE jobs.status`。

## 备选方案与取舍

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 内存态作业 | 实现简单，无迁移管理 | 重启即丢；失败需全量重跑；无法展示真实进度 | 否 |
| **状态落库 + checkpoint（采纳）** | 可续跑；进度可查；失败隔离到阶段 | 需迁移管理；checkpoint 失效策略必须显式声明 | 采纳 |

## 后果

### 正面

- 构建中 `SIGTERM` 重启后，作业可被识别并续跑（验收 28）；
- `qa` 失败后修正规则重跑，不必重跑 `render`。

### 负面（明确接受的代价）

- 阶段实现变更时若忘记递增版本号，"续跑"会复用语义已过期的产物——这是
  **静默错误**，比崩溃更危险；
- 需要维护数据库迁移（Alembic）。

### 需要后续跟进

- `STAGE_IMPL_VERSION` 的每次递增必须记入 `CHANGELOG.md`；
- 服务端测试覆盖"构建中重启 → 续跑"路径。
