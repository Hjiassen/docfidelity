# ADR-009 作业粒度：一个编排作业 + 多个子作业

- 状态：Accepted
- 日期：2026-09-17
- 关联：需求 3.2 场景 G、4.7、4.8、6.7 FR-M7-15/16；设计 DD-1.1、DD-11.4

## 背景

一个项目通常要产出多份文档，它们共用同一事实源与模板库，被同一次操作发起。

两种极端都不合适：

- **全部合成一个作业**：第 3 份文档失败，前 2 份成功的产物也拿不到，用户要等全部重跑；
- **完全独立无关联**：无法表达"这一批是一起发起的"，界面上也就无法给出整体进度。

## 决策

`Job` 分两种 kind，用 `parent_job_id` 建立父子关系：

```
编排作业（kind=orchestration）
  ├── 子作业 A（kind=document, doc_key=overview）
  ├── 子作业 B（kind=document, doc_key=detail）
  └── 子作业 C（kind=document, doc_key=testplan）
```

1. **失败隔离**：单个子作业失败不阻断其余子作业，成功的产物仍可下载；
2. **编排聚合状态由服务端计算**，规则唯一：

   ```
   全部 succeeded 且无待裁决  -> succeeded
   存在待裁决                -> awaiting_decision
   部分 succeeded 部分失败    -> partial_failure
   全部 failed                -> failed
   全部 canceled              -> canceled
   ```

3. `partial_failure` **仅编排作业**可取。

## 备选方案与取舍

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 单一作业 | 实现简单 | 单份失败即全败；无法局部重跑 | 否 |
| 完全独立作业 | 隔离彻底 | 无法表达批次；整体进度无处安放 | 否 |
| **编排 + 子作业（采纳）** | 失败隔离、局部重跑、批次进度可表达 | 需要派生器与聚合器；状态计算必须统一 | 采纳 |

## 后果

### 正面

- 注入单个子作业失败后，其余产物仍可下载（集成测试可覆盖）；
- 局部重跑只需重新派生失败的子作业。

### 负面（明确接受的代价）

- 聚合逻辑一旦在前端"顺手算一下"，就会出现两套规则——因此明确禁止前端推断；
- 父子作业的状态同步需要事务性保证，避免出现"父作业 succeeded 但子作业还在跑"。

### 需要后续跟进

- 聚合规则的唯一定义位置：`contracts.job.ORCHESTRATION_AGGREGATION_RULE`；
- 服务端 `JobStateMachine.apply` 为状态迁移唯一入口。
