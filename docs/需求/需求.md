## 1. 背景与目标

### 1.1 业务背景

**先明确适用范围：本系统不止于设计文档。** 下文以「交付类设计文档」作为**典型实例**引入问题域，但要解决的是一类普遍问题——凡是「存在外部给定的版式模板、章节结构可枚举、内容可由事实源推导」的文档，都在适用范围内：设计文档、需求与规格、测试文档、使用与运维手册、方案与报告、标准作业程序、招投标与验收文件、合规与审计材料等。**文档类型不是引擎的内置概念，而是可配置、可交换的数据资产**（见 2.6、4.9）。

以设计文档为例：交付文档（概要设计、详细设计、数据库设计等）受文件编号体系约束，必须严格沿用甲方给定的 Word 模板：封面、编制/审核/批准栏、修订记录、目录、页眉页脚、章节名称、自动编号、表格原型、图片槽位、页边距——任何一项偏离都会在评审时被打回。

同时，文档的内容事实源高度分散：接口定义在 FastAPI 的 OpenAPI 契约里，表结构在 ORM 与 Alembic 迁移里，模块协作在 proto 文件里，页面行为在 PRD 里，运行状态在截图里。人工把这些事实源"翻译"成符合模板体例的文档，是纯体力劳动，且极易出现"代码改了文档没改"的漂移。

**为什么开源。** 上述约束不是某个项目、某类文档的特例，而是所有「受模板管束的文档生产」的共性困境：有模板、有事实源、要评审、改一次要同步一遍。解决办法也是共性的——把模板解析为契约、把文档类型写成档案、把事实源统一接入、把合规判定规则化。这类能力没有商业机密属性，留在单个团队里只会重复建设；而**通用性只能靠多样性输入来验证**——开放出来，才可能积累到不同行业、不同文档类型的模板包与档案。

**开源不是发布动作，而是设计约束。** 这是本项目最重要的一条立场。若把开源当作"做完再放出去"，几乎必然失败——私有依赖、私有模板、私有路径会渗进核心链路，最终没有任何外部开发者能跑起来。因此本项目的开源属性必须在**第一行代码之前**就体现为约束：

1. **核心链路零私有依赖** —— 引擎的入库、编排、渲染、门禁四个环节不得依赖任何内部系统、内部约定或不可公开的数据；示例模板必须能演示全部能力（见 10.10）。
2. **对外契约即公共 API** —— 模板包格式、HTTP API、扩展点为对外承诺，一旦发布即受兼容性约束（见 4.5、10.6）。
3. **可验证性优先于功能量** —— 外部开发者必须能在离线、无 API Key 的条件下完整跑通并复现结果（见 10.9）。

### 1.2 问题域与需求来源

本系统的需求不是推演出来的，而是从一条真实跑通的"模板 + 事实源 → 交付文档"生产链路中提炼出来的。这条链路暴露的问题具有普遍性——**它们不是某个工具的缺陷，而是"外部给定的模板约束 + 多源异构事实 + 人工组装"这一模式的固有代价**。第 6 章的每一条功能需求，都在回应下表某一行。

| 序号 | 问题 | 实际表现 | 代价 |
| --- | --- | --- | --- |
| 1 | 模板样式难以对齐 | 同族文档的封面、目录样式不一致，根因是样式定义未同步（Normal / Title / 页眉 / 目录样式差异、页边距 1080 vs 1800 twips） | 反复 3 轮排查 |
| 2 | 分页策略无法约束 | 正文各章之间残留模板自带分页符，导致每章另起一页、页数虚高 | 需逐段定位清理 |
| 3 | 术语替换易出错 | 软件名替换时出现「…分析仪整体软件」这类连读重复 | 需特判修补 |
| 4 | 模板冗余内容难裁剪 | 参考资料模块必须移除（否则文档不能独立使用），但散落在标题、表格、文末说明共 4 处 | 需逐处定位 |
| 5 | 编排与版式耦合 | 内容生成与 OOXML 操作写在同一条代码路径里，任何版式调整都要改动内容逻辑 | 模块无法独立测试、无法复用 |
| 6 | 图片越界不可控 | Word 对超长图是"裁剪"而非跨页，页数检查发现不了，必须量 `wp:extent` | 需专门写越界检查 |
| 7 | 目录刷新引入假差异 | 刷新目录后 `_Toc` 书签 ID 变化，文本比对报出大量假差异 | 需归一化后比对 |
| 8 | 样式 ID 重映射漏项 | 跨文档克隆内容时只处理了段落样式、漏掉表格样式，导致多份文档的表样式错挂同一值 | 需双标签遍历修复 |
| 9 | 表格版式继承污染 | 模板 Normal 样式带的缩进被表格单元格继承，导致单元格内容换行 | 需固定单元格间距 + 清零缩进 |
| 10 | 体例无法沉淀 | 同类文档的不同文档类型体例完全不同（一接口一节 vs 一模块一表），全靠口头传递 | 需形式化为配置 |
| 11 | 模板解析重复劳动 | 每次生成都要现场读模板、比对样式；解析结果不落盘、不可检索、无版本 | 换项目要重踩一遍 |
| 12 | 成果零复用 | 构建逻辑与校验逻辑全部绑定单一项目，团队外无法使用；同类团队仍在手工排版 | 需按可复用引擎标准重新设计 |
| 13 | 单一文档类型写死 | 流程只认「设计文档」一种形态；换一类文档（需求、测试、手册、报告）就要另写一套，领域概念（接口 / 表）也散落在各层 | 需把文档类型与领域概念移出引擎（见 4.9） |

**结论**：这不是"写文档慢"的问题，而是**模板约束的复杂度已经超过人工可靠执行的阈值**。可靠解法只有一条——把模板变成契约、把**文档类型变成档案**、把事实源变成输入、把合规判定变成规则，并且让这四件事彼此解耦。其中第 13 条决定了这套解法是"只解决一类文档的一次性工程"还是"与文档类型无关的通用引擎"——这是本设计能否被他人复用的分水岭。

### 1.3 建设目标

本设计从零构建**可被他人复用的开源文档撰写引擎**，实现七个转变：

1. **从"写文档"到"定义模板与事实源"** —— 人只负责提供模板、事实源和裁决意见，组装与合规由系统完成。
2. **从"经验驱动"到"契约驱动"** —— 模板解析前置入库，形成可检索、可版本化的模板库；生成时查契约而非现场对比模板，体例成为配置而非口口相传。
3. **从"事后返工"到"门禁拦截"** —— 样式、版式、术语、完整性在构建阶段自动校验，不合格不出文档。
4. **从"自用脚本"到"可复用引擎"** —— 核心链路与私有数据彻底解耦，任何团队拿到自己的模板即可使用；模板能力以**模板包**形式沉淀与交换。
5. **从"单点工具"到"可扩展生态"** —— 事实源 Connector、门禁规则、渲染策略、Agent、模板包五类扩展点对外开放，能力由上游与社区共同补齐（见 4.5）。
6. **模型接管以实测为准** —— Agent 的每个决策点都必须有逐点基线与规则兜底；使用显式配置的模型，不以参数量或部署位置作为通过条件，模型不是运行前提（见 5.2）。
7. **从「为某类文档写工具」到「与文档类型无关」** —— 引擎不内置任何文档类型知识，也不内置任何领域概念；文档类型由**模板包 + 文档类型档案**声明，领域概念由**领域模型**声明；新增一类文档只写配置、不改引擎（见 4.9）。

### 1.4 设计原则

| 原则 | 含义 | 反例（来自 1.2 的真实问题） |
| --- | --- | --- |
| **模板零改动** | 输出文档从模板复制后编辑，模板原件不改；不新建第二套样式 | 用统一设置字体替换模板格式 |
| **样式层与内容层分离** | 只做"注入"，不做"重排"；样式层改动必须可追溯 | 直设格式覆盖样式导致模板失效 |
| **复用优先于新建** | 新章节/新表格复用同文档内已有原型 | 拿别模块的表克隆导致列宽错乱 |
| **只缩不放** | 图片、表格宽度只做收缩适配，不放大 | 小图被拉大糊掉 |
| **确定性构建** | 同输入同输出（易变 ID 除外），支持稳定比对 | 目录刷新导致假差异 |
| **可解释** | 每条自动决策（跳过、改写、判定）都有理由输出 | 静默跳过导致漏接口 |
| **Agent 边界清晰** | Agent 只做决策与判定，OOXML 读写与几何计算交确定性代码 | 让 LLM 改 numbering 定义 |
| **规则优先** | 能写成规则的绝不问 LLM | 用 LLM 判断表格宽度是否越界 |
| **依赖单向** | 契约模型为依赖之根；OOXML 读写只允许出现在渲染与门禁层 | 版式逻辑渗回内容编排层，导致模块无法独立测试与复用 |
| **开源即约束** | 核心链路零私有依赖；示例模板须能演示全部能力 | 把开源当作"做完再放出去"，外部开发者根本无法跑通 |
| **契约稳定优先** | 对外格式（模板包 / HTTP API / 扩展点）发布即承诺兼容 | 随意改 JSON 字段名，已入库的模板包与社区扩展全部失效 |
| **可复现优先** | 可离线验证、可复现的能力优先于功能数量 | 只能靠真实 API 才能验证，社区无法复现问题 |
| **实测准入、规则兜底** | 决策面收窄、结构化输出校验、候选注入、逐点基线；模型与部署方式由配置决定，质量下限由规则保障 | 未经逐点评测就让模型接管，或把更换模型当作质量保证 |
| **类型无关** | 引擎代码中不出现任何文档类型名称与领域概念名称；文档类型、体例、投影规则一律为外部数据 | 在渲染或编排层写 `if doc_type == "详细设计"` / `if kind == "endpoint"` |

## 2. 系统定位与范围

### 2.1 一句话定位

**本系统是一个开源、模板与体例驱动的通用文档撰写引擎：输入模板、文档类型档案与项目事实源，输出样式零偏差、体例合规、可追溯、可增量更新的定稿文档，并附全套质量报告。它不绑定任何特定文档类型——设计文档只是它的一种用法。**

**通用性如何成立（一句话）**：引擎只认「模板契约 + 文档类型档案 + 事实包 → 内容单元 → docx」这一条通路，**不认「接口」「数据表」「测试用例」这类领域概念，也不认「概要设计」「详细设计」这类文档类型**。领域概念由 Connector 与领域模型声明，文档类型由档案声明，二者都是外部数据（见 4.9）。

差异化的一句话：同类工具解决"内容怎么变成 Word"，本项目解决"**怎么在不破坏模板样式的前提下把内容放进去**"。后者的难点不在文本转换，而在 OOXML 样式层、编号、分页、版心与表格原型的保真——这正是本项目唯一难以被替代的能力。

作为开源项目，本项目的边界按三个层次划分，且这三层的**入库策略**是开源可行性的前提：

| 层次 | 内容 | 入库 |
| --- | --- | --- |
| **引擎** | 解析 / 契约 / 编排 / 渲染 / 门禁 / Agent 定义 | ✅ 开源本体 |
| **规范** | 模板包格式、内容 IR 格式、门禁规则格式、扩展点接口 | ✅ 开源本体 |
| **资产** | 模板 docx、项目事实源、产出文档、项目体例配置 | ❌ 永不入库（见 10.1） |

### 2.2 能力边界

| 做 | 不做 |
| --- | --- |
| 解析模板并建立**模板库**（模板包 + 版本管理），抽取样式契约、结构骨架、表格原型、图片槽位 | 修改模板原件 |
| 多源解析项目事实（OpenAPI / 代码 AST / ORM / proto / xlsx / Markdown / 截图） | 替代产品需求文档的编写 |
| 按模板体例生成章节、表格、图表、参数表 | 凭空编造未经事实源支撑的功能描述 |
| 模板深拷贝注入，样式层零改动落地 | 用统一样式"美化"模板文档 |
| 自动 QA 门禁：样式、版式、术语、完整性、追溯 | 替代人工评审签字 |
| 变更点驱动的增量更新与影响面分析 | 自动提交/发布文档 |
| 提供开放的扩展点（Connector / 规则 / 渲染策略 / Agent / 模板包） | 内置或分发任何真实业务模板 |
| 使用**显式配置且通过基线准入的模型**参与主流程，模型可完全关闭 | 依赖某个模型或外部 API 才能运行（见 5.2） |
| 覆盖任何满足适配判据（2.6.1）的文档类型：设计 / 需求 / 测试 / 手册 / 报告 / 作业程序 / 招投标等，新增类型以**配置**接入 | 为某一类文档做专用工具，或把文档类型与领域概念写死进引擎 |
| 提供**可自部署的 Web 工作台** | 提供 SaaS 服务、多租户或在线协同编辑 |

### 2.3 生态位与同类项目

公开发布意味着会被拿去和既有工具对比，本节的结论直接决定"别人为什么要用这个项目"：

| 同类项目 | 定位 | 与本项目的关系 |
| --- | --- | --- |
| `docxtpl`（Python，LGPL） | 用 Jinja2 语法渲染 docx 占位符 | **理念部分重叠**：都是"在已有 docx 上填内容"。差异见下方说明 |
| `vukan322/docforge`（Go，MIT） | DOCX 模板渲染库，明确"不修改文档样式" | **理念最接近**，但它是语言内库，不解决模板契约解析、结构骨架、门禁与事实源接入 |
| `gardener/docforge`（Go，Apache-2.0） | Documentation-as-Code，把多仓库 Markdown 聚合成文档包 | 同名但不同赛道：它做**源文档聚合**，不涉及 Word 模板保真 |
| `pandoc` | 通用文档格式转换 | 样式由 `reference.docx` 决定，与模板体例、版块原型、编号、分页无关 |
| `python-docx` / OpenXML SDK / `docx4j` | 底层 OOXML 读写 | 是**依赖**而非竞品 |
| 通用 LLM 写文档工具 | 提示词驱动的文档生成 | 无事实源约束、无模板保真、无门禁；产出不可复现 |
| 商业文档平台 | 模板管理 + 协作 + 审批 | 闭源、需上传资料、模板不可自控；本项目可离线、可审计、模板自持 |

**与"占位符填充"类工具的本质差异**（这是本项目的技术护城河）：

1. **约束来源不同** —— 占位符工具假设模板由使用者自己写、可随意改造；本项目的模板是**外部给定的、不可改动的**，且样式本身是评审对象。
2. **失败模式不同** —— 占位符工具填错最多是内容不对；本项目一旦样式层被改动、编号被重建、图片越界被 Word 裁剪，文档直接被打回。因此必须有**门禁**，而不只是渲染。
3. **输入不同** —— 占位符工具输入是"人整理好的数据"；本项目输入是**多源异构事实**（OpenAPI / ORM / proto / 变更点 xlsx），需要接入层与去重判定。
4. **通用性不同** —— 占位符工具的体例被写死在模板文件里，一类文档一套模板、一套填充代码；本项目把**文档类型、体例与投影规则外置为可交换档案**，同一引擎覆盖多类文档（见 4.9）。

### 2.4 开源分层与边界策略

| 层次 | 内容 | 归属与授权 |
| --- | --- | --- |
| **引擎核心** | 模板入库解析、契约模型、内容 IR、渲染策略、门禁引擎、Agent 定义 | 主仓库，Apache-2.0 |
| **规范** | 模板包格式规范、内容 IR 规范、门禁规则规范、扩展点接口 | 主仓库，Apache-2.0；破坏性变更受 10.6 约束 |
| **官方扩展** | 事实源 Connector（OpenAPI / ORM / proto / xlsx）、渲染后端 | 主仓库或官方独立包，同许可证 |
| **示例资产** | 自制示例模板与最小可跑用例，**必须能演示全部能力** | 主仓库（见 10.10） |
| **社区扩展** | 第三方 Connector、规则集、模板包 | 社区自持；主仓库只收录索引与规范符合性声明 |
| **私有资产** | 真实模板、事实源、产出文档、项目体例配置 | 永不入库（见 10.1） |

**明确不做 Open Core。** 不谈"社区版阉割 + 商业版完整"——本项目的价值集中在"契约解析 + 渲染保真 + 门禁"这条主链上，阉割任一环节，开源版就退化成普通的模板填充工具，项目也就失去了存在意义。开源版即完整版，差异只体现在**使用者自己的模板与事实源**上。

### 2.5 交付形态：当前只做 Web 端

**范围决策**：本期只交付 **Web 端**（服务端 + 浏览器工作台），不做 CLI、不做 MCP Server、不做独立 SDK 文档。

理由是使用者的真实操作链路是"上传模板 → 看解析结果 → 对不确定项裁决 → 接入事实源 → 触发构建 → 审阅报告 → 下载产物"——一条**强交互、多轮人工裁决**的流程。命令行下既难呈现（解析报告、差异清单、渲染目检图本质上是可视化产物），也不好发现下一步该做什么。

**但必须钉死一条边界：Web 端是引擎的前端，不是引擎本体。**

| 层 | 依赖方向 | 约束 |
| --- | --- | --- |
| **引擎内核**（Ingest / Registry / Compose / Render / QA） | **不依赖 Web** | 不得引入任何 Web 框架、HTTP、会话、前端相关依赖；保持"数据进、文档出"的可独立调用接口 |
| **服务端**（API / 作业调度 / 文件管理 / 权限） | 依赖引擎内核 | 只负责编排、状态、I/O 与访问控制；**不含任何 OOXML 逻辑** |
| **前端**（浏览器工作台） | 依赖服务端 API | 不承载业务规则与判断逻辑，只做呈现与交互 |

**为什么这条必须钉死**：1.2 第 5 条问题的教训是——内容生成与 OOXML 操作一旦耦合在同一条代码路径里，两者就无法分别演进。Web 化会引入一个同样危险的耦合：**渲染逻辑与 HTTP / 前端状态耦合**。一旦引擎内部出现 `request`、`session` 或前端字段名，它就既无法被单测、也无法被第三方扩展，更无法回到库形态使用——4.5 的五类扩展点会同时失效。

**部署形态**：以 **Docker 为主分发方式**（单容器或 Compose），默认本地 / 内网私有部署。原因见 10.11——模板是甲方资产，服务端一旦接收模板文件，就必须能明确回答"数据存在哪里、会不会发出外部"。这会直接影响开源项目的分发方式与兼容承诺（见 10.6）。

**信息架构**：页面结构、导航、字段与状态定义见**第 7 章**。上述边界在界面上体现为一条硬规则——**界面只做呈现、收集与裁决，不做业务判断**。

### 2.6 适用范围与通用性边界（重要）

通用性必须有判据，否则会滑向"什么都能做"的万能工具，最终什么都做不好。本节给出**适配判据、适用清单与明确不适用清单**。

#### 2.6.1 适配判据（三条须同时满足）

| # | 判据 | 说明 | 不满足时的表现 |
| --- | --- | --- | --- |
| 1 | **版式可外部给定** | 存在模板 docx，或可从一份既有文档逆向出可复用的样式层与版块原型 | 无版式约束的自由排版，本系统没有优势 |
| 2 | **结构可枚举** | 章节骨架、每章的块类型与必填槽位是有限的、可声明的 | 结构每份都不同，配置成本高于收益 |
| 3 | **内容可溯源** | 内容来自事实源（接口 / 表 / 条目 / 表单 / 数据 / 素材），或至少可被事实源校验 | 纯创作型写作（创意文案、散文）不在范围内 |

**三条是「与」关系。** 只满足前两条、内容纯创作 → 系统只能帮你排版，价值有限；只满足后两条、版式随心 → 模板库与保真能力用不上。

#### 2.6.2 适用文档类型（示例，非穷举）

| 族 | 典型文档类型 | 事实源示例 |
| --- | --- | --- |
| **软件交付类** | 概要设计、详细设计、数据库设计、接口设计、测试方案、部署方案 | OpenAPI、ORM / DDL、proto、测试用例、配置项 |
| **需求与规格类** | 需求规格说明书、产品需求文档、接口规格、验收规格 | 需求池、原型、业务规则表 |
| **验证与合规类** | 测试报告、验收报告、合规自查表、审计材料 | 测试结果、覆盖率、检查项清单 |
| **使用与运维类** | 用户手册、操作指南、安装部署手册、运维手册、FAQ | 界面截图、参数表、命令行、配置项 |
| **方案与报告类** | 技术方案、可行性报告、评估报告、项目周报 / 月报、复盘报告 | 数据表、指标定义、进度记录 |
| **流程与制度类** | 标准作业程序（SOP）、作业指导书、工艺文件、制度文件 | 流程图、岗位职责、表单、阈值 |
| **商务与招投标类** | 投标文件、技术标、应答书、报价说明 | 招标要求条目、资质清单、报价表 |

**这张表的意义**：它说明通用性不是口号——上表每一族都满足 2.6.1 的三条判据，因此**都不需要改动引擎**，只需新增模板包与文档类型档案（见 4.9.4 的接入成本分级）。

#### 2.6.3 明确不适用（写出来是为了省时间）

| 不适用 | 原因 |
| --- | --- |
| 无版式约束的一次性文档（通知、邮件、备忘） | 模板库与保真能力无收益，成本高于手工 |
| 纯创作型内容（创意文案、营销软文、散文） | 内容不可溯源，与「事实源为唯一真相」的前提冲突 |
| 以协作编辑为核心的场景（多人同时改一份文稿） | 本系统是「生成器」而非「在线编辑器」，不做协同编辑 |
| 需要复杂排版设计的出版物（画册、杂志版式） | 版式本身即创作对象，不适合由契约驱动 |
| 结构完全自由、无重复性的文档 | 结构不可枚举，配置成本无法摊薄 |

**一条纪律**：**新增适用范围必须先进 2.6.2 的表、并逐条给出适配判据的说明**；三条中任一条不成立，该场景应作为**独立产品**而不是本系统的功能扩展。这条用于防止通用性滑向范围蔓延（见第 13 章）。

## 3. 用户与使用场景

### 3.1 角色定义

开源项目的角色分两类：**使用者**（消费能力）与**贡献者**（生产能力）。二者的关注点不同，系统必须同时满足——这是把内部工具做成开源项目的关键差异。

**使用者**

| 角色 | 职责 | 系统关注点 |
| --- | --- | --- |
| **文档工程师** | 接入模板与事实源，裁决体例冲突，定稿 | 配置成本低、可复现、报告可读 |
| **评审人 / 质量** | 评审交付文档是否符合模板与体例 | 合规报告、追溯矩阵、变更留痕 |
| **模块负责人** | 提供接口 / 表 / 页面的设计事实 | 只需维护事实源，不必关心排版 |
| **平台维护者** | 部署与运维本系统的 Web 服务；维护模板库、规则库 | 部署与升级、模板包版本管理、规则配置、备份与清理 |

**贡献者**

| 角色 | 典型贡献 | 门槛要求 |
| --- | --- | --- |
| **Maintainer** | 架构决策、版本发布、RFC 裁决 | 需理解全链路 |
| **核心贡献者** | 引擎代码、扩展点实现、门禁规则 | 需 Python 与 OOXML 基础 |
| **模板包作者** | 贡献某类模板的解析适配与体例配置 | **只需提供模板 + 一份配置，不必写代码**（见 10.8） |
| **集成开发者** | 接入本团队的事实源，部署并维护本系统 | 需阅读扩展点与部署文档 |
| **问题报告者** | 提交可复现的最小样例 | 需提供**自制脱敏样例**，不得附真实文档（见 10.1） |

**关键设计要求**：**模板包作者必须是不写代码的角色。** 模板多样性是本项目最需要的社区输入，若贡献模板包需要读源码，这类贡献量会趋近于零。因此模板适配必须是纯声明式的（配置 + 约定目录），不要求贡献者理解 OOXML。

### 3.2 核心场景

**场景 A：新建一套交付文档（主流程）**

1. **模板入库**：上传一套参考模板（示例：概要 / 详细 / 数据库三份；换成其他文档类型同理），系统一次性解析为模板包（原件 + 契约 + 版块索引 + 指纹）并登记到模板库；同时登记对应的**文档类型档案**。
2. 查看入库报告，确认样式契约、结构骨架、表格原型、版块索引、待清理占位清单无误；对解析不确定项做一次性裁决。
3. 接入事实源：接口契约、ORM / 迁移定义、协议文件、截图与设计图、需求文档。
4. 配置生成清单：文档族、术语表变量、分页策略、章节装配映射、版块引用（如封面取 A 模板、修订表取 B 模板）。
5. 一键构建 —— 生成期只读模板包契约；系统派生**一个编排作业 + 按文档族数量的子作业**，各自产出 docx，最后汇总为整套产物 + 全量 QA 报告。
6. 查看 QA 报告，对未通过项逐条裁决（改配置 / 改事实源 / 人工豁免）。
7. 定稿归档。

**场景 A′：后续再生成（模板库已就绪）**

1. 指定模板包版本（或默认最新）与事实源，一键构建。
2. 不再有"解析模板"这一步，也不与模板做对比——所有版式决策直接来自模板包契约。

**场景 B：接口变更后增量更新**

1. 导入变更点 xlsx（序号 / 模块 / 接口路径 / 方法 / 接口名称 / 关联变更点）。
2. 系统从代码提取接口规格，与目标文档已登记接口做**路径去重 + 功能去重 + 约束排除**三重判定。
3. 输出判定表（已存在 / 功能重复 / 约束排除 / 拟新增 / 待确认）与章节落位方案。
4. 人工确认后，按模板深拷贝方式注入新接口段落与数据行，并挂批注（实现位置 + 来源变更点）。
5. 输出增量 diff 报告与影响面清单。

**场景 C：模板升级换版**

1. 上传新版模板 → 入库时自动与上一版本指纹比对，输出变更点（样式 / 结构 / 表原型 / 页面设置）与影响面。
2. 列出受影响的历史文档及其章节。
3. 选择"重新生成"（沿用新模板包重新装配内容）或"样式层迁移"（只换格式、不动文字内容）。

**场景 D：文档漂移巡检**

1. 定时拉取代码仓库的接口与表结构变更。
2. 与已交付文档的事实快照比对，标出"代码已改、文档未改"的章节。
3. 生成漂移清单与建议修订项。

**场景 E：外部团队首次接入（换一套完全不同的模板）**

开源项目的成败取决于这条路径是否足够短。目标：**从 clone 到产出第一份文档 ≤ 30 分钟，且全程不需要 API Key。**

1. `git clone` → 安装 → 运行示例用例（自制示例模板 + 内置样例事实源），完整走通"入库 → 构建 → 门禁 → 出文档"。
2. 放入本团队模板 → 入库解析 → 查看**入库报告**（识别到的样式、结构骨架、表格原型、槽位，以及**解析置信度与待确认项**）。
3. 对解析不确定项做一次性人工确认，结果写入声明式覆盖配置（`template.overrides.yaml`），**不改代码**。
4. 接入事实源——先用最小输入（一份 Markdown 或 CSV）跑通，再逐步替换为 OpenAPI / ORM 等 Connector。
5. 构建并查看门禁报告，逐条裁决未通过项。

**场景 F：社区贡献一个模板包或一条规则**

1. 按模板包格式规范准备目录，撰写声明式体例配置（**无需编写 Python**）。
2. 本地执行规范自检命令，确认结构、字段、必填槽位合规。
3. 提交 PR，附**自制脱敏样例模板**作为回归用例（不得附真实模板，见 10.1）。
4. CI 自动执行：规范符合性校验 + 端到端回归 + 现有模板包不退化。
5. 合入主仓库的**模板包索引**；或由贡献者自持仓库，只在索引中登记与声明符合性。

**场景 G：Web 端长任务的处理方式（Web 化的第一个技术难点）**

文档构建是分钟级任务（详细设计 63 页，含目录刷新、PDF 导出、逐页目检），**同步 HTTP 请求必然超时**，因此构建必须作业化：

1. 点击"开始构建" → 立即返回**作业 ID**，界面进入作业详情页，请求不阻塞。
2. 子作业内按阶段执行（入库 → 编排 → 渲染 → 刷新 → 门禁）；**编排作业聚合推送「子作业 n/N + 当前阶段」**，进度实时可见。
3. 任一子作业失败，界面定位到具体子作业与阶段；可**只重跑失败子作业**，或对某子作业**从失败阶段续跑**——**单份失败不牵连其余文档**。
4. 作业产物（docx / QA 报告 / 渲染目检图）按子作业落入工作区；编排作业提供整套下载与历史版本对比。

**硬约束**：**作业状态必须持久化**。服务重启后，未完成作业须可识别、可续跑或可重试——否则"构建到一半重启服务就丢工作"，这在本地自部署场景下几乎必然发生。

**场景 H：配置模型参与主流程并可降级**

1. 部署时填写显式授权的 OpenAI 兼容端点与模型名，按探测结果启用结构化输出能力并加载匹配的逐点基线；界面如实显示模型状态、调用边界与脱敏范围，不因端点名称推断「无外部请求」（见 10.11）。
2. 发起构建：模板解析、版式决策、门禁判定等**规则类决策点全程不调用模型**；语义判重、章节落位等**模型类决策点**在检索裁剪后的上下文中做封闭选择。
3. 任一模型类决策点输出校验失败、置信度缺失或低于阈值 → 默认走规则值并标记**待确认**，构建继续；这些项在门禁报告与裁决待办中可见。替代准入策略须符合 5.2.4。
4. 关闭模型后重复构建：文档仍产出并通过门禁（文案退化为模板化描述），用于验证降级路径（对应验收 37–41）。

**场景 I：接入一类全新的文档类型（通用性的主路径）**

1. **判断适配性**：逐一核对 2.6.1 的三条判据；三条全满足才继续（否则应作为独立产品评估，而不是本系统的功能扩展）。
2. **确认领域模型**：所需领域类型若已注册则直接复用；缺失的按 L2 追加声明（必要时补一个 Connector），**不写代码分支**。
3. **模板入库**：上传该类文档的模板 → 得到模板包（L0）。
4. **写文档类型档案**：章节骨架、允许的内容单元类型、投影规则（`for_each` / `group_by` / `layout` / 字段映射）、门禁规则集、模板包引用、术语作用域——**纯配置，不写 Python**（L1）。
5. **最小试跑**：用一份最小事实源构建 → 查看门禁报告 → 调整档案 → 直到通过。
6. **归档与交换**：档案可打包交付给其他团队复用（验收 44、45）。

**判据**：全程引擎代码零改动。若某一步必须改引擎，说明抽象存在缺口——应走 RFC 修抽象，而不是就地打补丁（见 4.9.4）。

## 4. 总体架构

### 4.1 五层架构

```
┌─────────────────────────────────────────────────────────────┐
│  L5 交互层    Web 工作台 · API 服务 · 作业进度推送            │
├─────────────────────────────────────────────────────────────┤
│  L4 门禁层    QA Gate：样式·版式·术语·完整性·追溯·渲染目检    │
├─────────────────────────────────────────────────────────────┤
│  L3 渲染层    Render：模板深拷贝 · 样式对齐 · 编号统一 ·      │
│               分页策略 · 表格规范化 · 图片自适应 · 域刷新      │
├─────────────────────────────────────────────────────────────┤
│  L2 编排层    Compose：内容 IR · 章节装配 · 接口/表/图生成 ·  │
│               术语变量 · 文案生成                             │
├─────────────────────────────────────────────────────────────┤
│  L1 库层      Registry：模板库（原件+契约+版块+指纹）·       │
│               模板检索与版本比对 · 事实源注册中心              │
├─────────────────────────────────────────────────────────────┤
│  L0 接入层    Ingest：docx 模板 · OpenAPI · AST · ORM/DDL ·   │
│               proto · xlsx · Markdown · 图片素材              │
└─────────────────────────────────────────────────────────────┘
```

**Agent 的位置**：Agent 不占单独的层，而是**横切在 L1–L4 之上**——Curator 驱动 L1 模板入库，Architect / Composer 驱动 L2 编排，Renderer 驱动 L3 渲染，Inspector 驱动 L4 门禁。各层的确定性操作始终是普通 Python 函数，以 function tool 形式暴露给 Agent（详见 5.4、5.5）。

**关键设计决策一**：**编排层与渲染层必须解耦**。把内容生成与 OOXML 操作放在同一条代码路径里，会导致任何版式调整都要改动内容逻辑——这是 1.2 第 5 条问题的直接来源，也是本设计首要规避的对象。解耦后，内容以 **Content IR** 表达，渲染层只负责"把 IR 按模板契约落地"。

**关键设计决策二**：**模板解析前置**。模板解析属于**入库流程**（M2），不属于生成流程。生成期只查模板包契约，不再读模板做比对——这是把解析成本从 O(N) 降到 O(1)、让模板成为可复用资产的前提。详见 4.4。

**关键设计决策三**：**Agent 只做决策，不做 OOXML 操作**。Agent 层横切在五层之上负责编排与判定，所有对文档的精确读写由 L3 的确定性工具完成。这是"确定性构建"能成立的前提，详见 5.3。

**关键设计决策四**：**Web 端是引擎的前端，不是引擎本体**。L5 只承载交互、会话状态与作业进度；引擎内核（L0–L4）不引入任何 Web 依赖；服务端只做编排、作业与 I/O，不含 OOXML 逻辑。这条与决策一同源——上一次是"内容与版式"耦合，这一次要防的是"渲染与 HTTP / 前端状态"耦合，详见 2.5。

**关键设计决策五**：**契约模块是依赖之根**，OOXML 能力只允许出现在渲染层与门禁层。这是决策一在工程上的落地方式：内容层、编排层、API 层均不得直接操作 OOXML，只能通过契约模型传递数据。依赖方向单向且**可自动校验**，从根本上防止「版式逻辑重新渗回上层」（见 4.6）。

**关键设计决策六**：**引擎与文档类型无关**。引擎代码中不得出现任何文档类型名称（`概要设计`、`详细设计`…），也不得出现任何领域概念名称（`接口`、`数据表`、`测试用例`…）。文档类型由**文档类型档案（Doc Type Profile）**声明，领域概念由**领域模型（Domain Model）**声明，二者都是外部数据。这是把"通用性"从口号变成工程属性的唯一办法，也是可自动检索校验的（见 4.9、NFR-28、验收 42）。

### 4.2 核心概念模型

| 概念 | 定义 | 载体 |
| --- | --- | --- |
| **Template Registry（模板库）** | 模板包的集中存储、检索与版本管理；生成时按 `template_id@version` 取用，不再现场解析模板 | 目录 + 索引 JSON |
| **Template Package（模板包）** | 模板入库一次的完整产物：原件 docx + 契约 + 版块索引 + 素材 + 指纹 | 目录（docx + JSON） |
| **Template Contract（模板契约）** | 模板的可校验数字化表达 | JSON |
| **Style Contract（样式契约）** | 样式名 / styleId / basedOn / 字体 / 字号 / 行距 / 段距 / 缩进 / 页边距 | JSON |
| **Outline Skeleton（结构骨架）** | 章节树 + 每章节允许的块类型与槽位 | JSON / YAML |
| **Block Library（版块库）** | 封面、修订记录、目录、页眉页脚、章节块、表格原型的可复用单元 | docx 片段 + 描述 |
| **Template Fingerprint（模板指纹）** | 用于版本比对与变更检测的稳定摘要 | JSON |
| **Content IR（内容中间表示）** | 与格式无关的内容描述（heading / para / bullets / table / figure / screenshot / trace） | YAML / Python DSL |
| **Domain Model（领域模型）** | 对「被文档化的对象」的规范化描述：领域类型、字段 schema、标识键、可比较字段、可追溯字段；**不含任何文档概念** | 声明式 schema（YAML / JSON） |
| **Domain Object（领域对象）** | 领域模型的一个实例：一条接口、一张表、一个测试用例、一道工序…… | 事实包内的条目 |
| **Doc Type Profile（文档类型档案）** | 一类文档「怎么写」的完整声明：适用判据 + 体例 + 投影规则 + 规则集 + 模板包引用 + 术语作用域 | 目录（YAML + 引用） |
| **Genre Schema（体例）** | 档案中「章节骨架 + 内容单元类型 + 体例约定」的部分，即原本靠口头传递的写作规范 | YAML |
| **Projection Rule（投影规则）** | 把领域对象装配为内容单元的声明式规则（`for_each` / `group_by` / `layout` / `fields` / `columns`） | YAML / DSL |
| **Content Unit（内容单元）** | 内容 IR 中的语义块，只含抽象块类型 + 体例声明的字段；不含领域概念与 OOXML 概念 | IR 节点 |
| **Fact Source（事实源）** | 唯一可信的项目事实 | OpenAPI / AST / ORM / proto / xlsx |
| **Fact Snapshot（事实快照）** | 构建时刻的事实摘要，用于漂移检测 | JSON |
| **Trace Matrix（追溯矩阵）** | 需求 ↔ 接口 ↔ 数据表 ↔ 文档章节 的双向映射 | CSV / JSON |
| **QA Report（质量报告）** | 门禁结果，含规则、命中位置、严重级别、豁免记录 | Markdown / JSON |
| **Fact Bundle（事实包）** | 一次事实源接入产生的规范化事实集合，带来源、定位与可信级别 | JSON |
| **Rule / Finding / Waiver（规则 / 命中 / 豁免）** | 门禁三要素：规则定义、规则命中记录、经人工裁决的豁免记录 | YAML / JSON |
| **Stage（阶段）** | 作业内可续跑的执行单元，是进度呈现与断点恢复的最小粒度 | 作业记录的一部分 |
| **Artifact（产物）** | 作业输出的可下载物：docx、QA 报告、渲染目检图、事实快照、复现包 | 文件 |
| **Job（作业）** | Web 端长任务的执行单位：状态持久化、按阶段推进、可取消 / 续跑 / 重试 | 数据库记录 + 工作区产物 |

### 4.3 设计约束矩阵（问题 → 约束 → 落点）

1.2 的 13 条问题必须逐条落到一条**可执行的设计约束**上，否则设计就没有真正回应它。本表是需求评审与后续回归的检查清单：**凡无法对应到约束的问题，视为尚未被设计覆盖**；凡找不到来源问题的约束，视为过度设计。

| # | 问题 | 设计约束 | 落点 |
| --- | --- | --- | --- |
| 1 | 模板样式难以对齐 | 生成期不得自行拼装样式；样式只能来自模板包契约，以「原件负责渲染、契约负责校验」落地 | 4.4、6.2、6.4 |
| 2 | 分页策略无法约束 | 分页成为**声明式策略**：显式声明必须分页的版块与连排区间，其余一律清理 | FR-M4-05、FR-M5-04 |
| 3 | 术语替换易出错 | 术语一律经**变量替换 + 连读重复检测**，禁止在多处文本中硬编码 | FR-M3-09、FR-M5-08 |
| 4 | 模板冗余内容难裁剪 | 裁剪以**声明式规则**表达，且必须定位到「标题 + 段落 + 表格」完整块 | FR-M2-10 |
| 5 | 编排与版式耦合 | 分层与**依赖规则**强制单向；契约模型为依赖之根，OOXML 只出现在渲染与门禁层 | 4.1 决策一 / 五、4.6 |
| 6 | 图片越界不可控 | 图片尺寸由**几何计算**决定并逐张校验；禁止以页数间接判断 | FR-M4-07、FR-M5-07 |
| 7 | 目录刷新引入假差异 | 一切比对前先归一化易变标识；禁止以字节或绝对 ID 作为判等依据 | FR-M5-11、10.9 |
| 8 | 样式 ID 重映射漏项 | 跨文档克隆必须**同时**处理段落样式与表格样式 | FR-M2-09、FR-M5-01 |
| 9 | 表格版式继承污染 | 关键表格的单元格版式固定，不继承宿主样式 | FR-M4-08 |
| 10 | 体例无法沉淀 | 体例以**配置**表达、按文档类型隔离，不进入代码 | FR-M3-10、8.4 |
| 11 | 模板解析重复劳动 | 解析前置到**入库流程**，生成期只查契约（成本 O(n) → O(1)） | 4.4、6.2（1） |
| 12 | 成果零复用 | 内核零私有依赖、零 Web 依赖；五类扩展点对外稳定 | 2.4、2.5、4.5 |
| 13 | 单一文档类型写死 | 文档类型、体例与「领域 → 内容」的映射一律为**外部数据**；引擎代码不得出现文档类型与领域概念名称 | 4.9、NFR-28、验收 42 |

**新增需求（非问题来源）**：1.3 第 6 条与 1.4「实测准入、规则兜底」原则来自**建设目标**，不是上表 13 条问题之一，因此不占问题编号。其设计约束为——**每个决策点必须显式归为规则 / 配置模型 / 可选模型 / 人工，且模型不可用时链路仍然成立**。落点见 5.2、NFR-23~NFR-27、验收 37–41。按本节判据，它属于**已被约束覆盖**的需求，不算过度设计。

### 4.4 模板库与模板包结构

#### 4.4.1 核心转变：解析前置，一次入库多次生成

最直接的做法是**生成时现场解析模板**：每次构建都打开模板、读样式、与目标文档比对、对齐、再注入。这意味着解析成本随生成次数线性增长，而且同一模板的坑会被反复踩——这是 1.2 第 11 条问题的根因。

改为**入库时解析一次、生成时查契约**：

| | 反例（生成时对比模板） | 本设计（模板库前置） |
| --- | --- | --- |
| 解析时机 | 每次生成时 | 模板入库时一次 |
| 解析成本 | O(生成次数) | O(1) |
| 结果沉淀 | 无，用完即弃 | 固化为模板包，可复用 |
| 换项目 | 重踩一遍 | 直接复用，仅适配差异 |
| 模板换版 | 无法判断改了哪些 | 指纹比对输出变更点与影响面 |
| 跨模板组合 | 手工写死（如封面取 014、修订表取 006） | 按 `block_id` 引用，配置表达 |

```
【入库 · 一次性】
  模板 docx ──解析──▶ 模板包（原件 + 契约 + 版块索引 + 指纹）──▶ 模板库

【生成 · 每次】
  模板库取包 ──▶ 查契约（结构/样式/版心/槽位）──┐
  事实源     ──▶ 编排内容 IR ──────────────────┴──▶ 深拷贝原件 ──▶ 注入 ──▶ 门禁 ──▶ 输出
```

#### 4.4.2 必须钉死的边界：契约是索引，不是渲染材料

**JSON 契约不能替代原始 docx，生成时的深拷贝仍必须读原件。** 原因：

1. `styles.xml` 含 JSON 难以穷尽表达的定义——`tblStylePr type="firstRow"` 条件格式、theme 颜色/字体引用、东亚字体、`settings.xml` 的兼容性开关；
2. `numbering.xml` 的 `abstractNum` / `num` 层级结构与缩进，重建即改变编号外观；
3. `theme1.xml` / `fontTable.xml` 的主题字体方案，重建会导致字体回退；
4. 页眉页脚部件、`rels` 关系、图片部件、`customXml`；
5. 封面段落、修订记录表等版块原型必须**从原件深拷贝**，JSON 描述无法还原。

因此模板包是**"原件负责渲染、契约负责查询与校验"**的双材料结构。任何"用 JSON 重新造一份模板"的做法都会导致样式全丢，明确禁止。

#### 4.4.3 模板包目录结构

```
templates/<template_id>@<version>/
├── manifest.json          # 元信息：文件编号、版本、文档类型、入库时间、包哈希
├── source.docx            # 原件（只读，深拷贝源；永不修改）
├── contract/
│   ├── styles.json        # 样式契约：name / styleId / type / basedOn / rPr / pPr
│   ├── page_setup.json    # 页面设置：pgSz / pgMar / 分节数与分节差异
│   ├── numbering.json     # 编号定义：abstractNum / num / 标题样式绑定的 numId
│   ├── used_styles.json   # document.xml 实际引用的 pStyle / tblStyle 及次数
│   └── outline.json       # 结构骨架：章节树 + 样式 + 编号 + 块类型 + 槽位
├── blocks/
│   ├── cover.json         # 封面：段落索引范围 + 原型定位规则
│   ├── revision.json      # 修订记录表：定位规则 + 列结构 + 固定单元格版式
│   ├── toc.json           # 目录：sdt 范围 + 标题样式 + 允许的层级深度
│   ├── headers.json       # 页眉页脚：文本 + 边框状态 + 分节继承关系
│   └── tables.json        # 表格原型清单：列数 / 列宽 / 表头样式 / 所属章节
├── assets/
│   └── images/            # 模板内图片，作为图片槽位与尺寸参考
├── placeholders.json      # 待清理的模板编写说明与占位提示
└── fingerprint.json       # 模板指纹：用于版本比对与变更检测
```

#### 4.4.4 契约如何替代"现场对比模板"

生成阶段每一项原本需要打开模板现算的决策，改为查契约：

| 生成时的决策 | 反例（现场读模板） | 本设计（查契约） |
| --- | --- | --- |
| 二级标题用哪个样式渲染 | 打开模板找 Heading 2 | `contract/outline.json` → styleId |
| 该章节允许放哪些块 | 无约束，靠人记 | `contract/outline.json` → 块类型白名单 |
| 表格列宽取多少 | 打开模板量 `tblGrid` | `blocks/tables.json` → 列宽 |
| 版心宽是多少 | 现场算 `pgSz - pgMar` | `contract/page_setup.json` |
| 封面段落格式 | 现场读模板封面 | `blocks/cover.json` + 原件深拷贝 |
| 有哪些槽位必须填 | 现场扫模板 | `contract/outline.json` → slots |
| 该用哪个编号 | 现场查 numbering | `contract/numbering.json` |
| 模板是否换版 | 无法判断 | 比对 `fingerprint.json` |
| 修订记录表复用哪份 | 手工写死模板名 | `blocks/revision.json` 按 `block_id` 引用 |

#### 4.4.5 版本与指纹

- **标识**：`template_id` 取模板封面 / 页眉中的文件编号（如 `DOC-XXX-014`），`version` 取模板版本号（如 `1.0`）。
- **多版本共存**：同一 `template_id` 的不同版本同时保留，生成时显式指定；不指定则用最新版并提示。
- **入库自动比对**：新版本入库时与上一版本指纹 diff，输出样式层 / 结构 / 表原型 / 页面设置的变更清单与影响面。
- **可追溯**：每份产出文档记录其使用的模板包哈希，可反查"这份文档基于哪一版模板生成"。
- **指纹稳定性**：指纹计算前必须归一化易变标识（如 `_Toc` 书签 ID、部件关系 ID），否则每次打开保存都会产生假差异。

### 4.5 扩展点设计与稳定度分级

开源项目必须回答一个容易被忽略的问题：**哪些接口是对外承诺、哪些随时可改？** 承诺不清，贡献者不敢写扩展（怕白写），使用者不敢依赖（怕升级即坏）。本节把扩展点及其稳定度明确下来。

**五类扩展点**

| 扩展点 | 作用 | 接入方式 | 稳定度 |
| --- | --- | --- | --- |
| **Connector** | 把某类事实源（OpenAPI / ORM / proto / xlsx / Markdown）转为统一事实模型 | 实现协议 + 注册入口；官方提供参考实现 | Stable |
| **QA Rule** | 门禁规则：样式、版式、术语、完整性、追溯 | 声明式规则（YAML）为主，复杂规则可写断言函数 | Stable |
| **Template Pack** | 一类模板的解析适配**与文档类型档案（体例 + 投影规则）** | **纯声明式目录 + JSON/YAML**，不要求写代码 | Stable（格式版本化） |
| **Renderer Strategy** | 版式落地策略：分页、表格规范化、图片自适应、编号处理 | 声明式策略配置 + 可选自定义后端 | Beta |
| **Agent** | 决策与判定环节（判重、体例裁决、评审） | instructions + 工具集 + handoff 声明 | Experimental |

**稳定度定义**

| 级别 | 承诺 |
| --- | --- |
| **Stable** | 破坏性变更必须升主版本；变更前至少一个小版本标记弃用并给出迁移指引 |
| **Beta** | 可在次版本变化，但必须在 CHANGELOG 明示并给出替代方案 |
| **Experimental** | 不承诺兼容，可能随时调整 |

**为什么 Agent 只能定 Experimental，而模板包与规则定 Stable？**

因为两者的变化驱动不同。模板包与门禁规则是**纯数据契约**，可以先冻结再演进；而 Agent 的行为直接依赖模型能力，模型升级时提示词与工具描述几乎必然要调整。若强行承诺 Agent 接口稳定，就会出现"为了兼容旧提示词而拒绝升级模型"的荒谬局面。**把稳定度分层，本质上是把"可冻结的东西"与"必然演进的东西"分开承诺。**

**三条硬原则**

1. **扩展点必须能脱离 Agent 使用。** 每个扩展点在服务端调用与 Python API 上都能独立使用（CLI 后置），不强制经过 Agent 编排——否则 LLM 关闭时生态即失效（呼应 NFR-13 / OS-14）。
2. **发现机制不侵入核心。** 走标准 entry points 声明，第三方包安装后自动被发现，核心代码不含任何第三方名称。
3. **扩展点不得成为保真的后门。** 任何扩展点都不能绕过 L3 渲染层直接写 OOXML——若能绕过，样式保真承诺即形同虚设（呼应 5.3 的 Agent 边界）。

### 4.6 模块分解与依赖规则

本节回答"这套系统由哪些模块组成、谁可以依赖谁"。它是 4.1 五条决策的工程落地，也是**全新设计与改造旧实现的分界线**——模块边界在第一天划定，之后所有代码都必须落在边界之内。

#### 4.6.1 模块清单

| 模块 | 职责 | 关键产出 |
| --- | --- | --- |
| `contracts` | 全部对外数据模型与格式规范的唯一出处：模板包、契约、内容 IR、事实包、配置、报告 | Pydantic 模型 + JSON Schema |
| `ooxml` | **唯一**允许直接读写 OOXML 的基础设施：部件、样式、编号、几何、图片、域 | 低层原语 |
| `model` | 领域模型与投影：领域类型注册与校验、投影规则求值（**不含文档概念**，见 4.9.1） | 领域对象集合 + 内容单元序列 |
| `ingest` | 事实源接入：把各类外部输入规范化为领域对象与事实包 | Fact Bundle |
| `registry` | 模板入库解析与模板库：解析、契约生成、指纹、检索、版本比对；**文档类型档案的登记、检索与版本管理**（见 4.9.2） | Template Package + Doc Type Profile |
| `compose` | 内容编排：按文档类型档案（骨架 + 投影规则）把领域对象装配为内容 IR | Content IR |
| `render` | 版式落地：把内容 IR 按模板包与渲染策略落成 docx | docx |
| `qa` | 门禁规则引擎：规则加载、判定、严重级别、豁免、报告 | QA Report |
| `pipeline` | 阶段机与作业编排：阶段定义、进度、断点续跑、留痕（**纯逻辑，不依赖 HTTP**） | Job 状态与事件 |
| `agents` | Agent 定义、instructions、工具面装配、护栏 | Agent 定义 |
| `api` | Web 服务端：HTTP 接口、SSE 推送、文件与访问控制 | REST + SSE |
| `web` | 浏览器工作台 | 界面 |
| `cli` | 命令行薄壳（**后置**，本期不交付） | — |

#### 4.6.2 依赖规则（可自动校验）

| 模块 | 允许依赖 | 明确禁止 |
| --- | --- | --- |
| `contracts` | 仅 `pydantic` | 其余一切内核模块 |
| `ooxml` | `contracts` | `compose` `registry` `pipeline` `api` `web` |
| `model` | `contracts` | **`ooxml`** `render` `qa` `registry` `api` `web` |
| `ingest` | `contracts` | `ooxml` `registry` `render` `qa` `api` |
| `registry` | `contracts` `ooxml` | `compose` `render` `qa` `api` |
| `compose` | `contracts` `ingest` `model` | **`ooxml`（关键）** `registry` `render` `api` |
| `render` | `contracts` `ooxml` | `compose`（只接收 IR，不回读编排内部）`api` |
| `qa` | `contracts` `ooxml`（只读） | `api` `web` |
| `pipeline` | 上述全部内核模块 | **`api` `web`** |
| `agents` | `contracts` + `pipeline` 暴露的工具面 | `web` |
| `api` | `contracts` `pipeline` | **`ooxml`（关键）** `registry` 内部实现 |
| `web` | 仅 HTTP | 一切内核模块 |

三条硬规则：

1. **单向** —— 依赖只能沿 `web → api → pipeline → {compose, registry, ingest, render, qa} → {ooxml, model} → contracts` 流动，**禁止循环依赖**。`model` 与 `ooxml` 平行且互不依赖：领域概念与 OOXML 概念不得互相污染（见 4.9.1）。
2. **唯一出口** —— OOXML 能力只有一个出口（`ooxml`）。任何模块绕过它直接改 XML，等于破坏样式保真承诺，须**由依赖门禁自动拦截**（见 OS-06、验收项 32）。
3. **零上下文** —— `pipeline` 及其以下不得感知「请求、会话、前端」。作业是数据结构，不是 HTTP 上下文；这是决策四的落地方式。

#### 4.6.3 关键接口（模块之间的缝）

模块之间只通过这些接口通信。它们是**内部契约**（可随主版本演进）；带 ★ 的必须有对应 JSON Schema，因为同时是未来的扩展点（见 4.5）。

| 接口 | 形态 | 输入 → 输出 |
| --- | --- | --- |
| `FactSourceConnector` ★ | Protocol | 源配置 → 领域对象 + 事实包 |
| `DomainModelRegistry` ★ | 只读接口 | 领域类型名 → 字段 schema / 标识键 / 可比较字段 |
| `ProjectionEvaluator` ★ | Protocol | 领域对象集合 + 投影规则 → 内容单元序列 |
| `TemplateParser` | Protocol | 模板 docx → 模板包 |
| `ContractQuery` | 只读接口 | 模板包 → 版式决策（样式 / 骨架 / 列宽 / 版心 / 槽位 / 编号） |
| `Composer` | Protocol | 领域对象集合 + 文档类型档案 → 内容 IR |
| `RendererStrategy` ★ | Protocol + 声明式配置 | 内容 IR + 模板包 → docx |
| `Rule` / `RuleSet` ★ | 以声明式 YAML 为主 | 文档 + 模板包 + 上下文 → 命中列表 |
| `Stage` / `Pipeline` | Protocol | 作业定义 + 续跑起点 → 作业结果与事件 |
| `ArtifactStore` | Protocol | 产物 → 归档位置与哈希 |

**接口先行原则**：上述接口在编码开始前先以 Pydantic 模型与 Protocol 落定，再并行开发两侧实现。这既是解耦手段，也是让"内核可在无 Web 环境下测试"（验收 32）可被验证的唯一方式。

### 4.7 核心数据模型

本节给出支撑上述结构的主要数据结构。字段为首版定义，完整规范随实现落入 `docs/spec/`；**所有对外格式都带 `format_version`**，受 10.6 兼容承诺约束。

**（1）模板包（Template Package）**

| 对象 | 关键字段 |
| --- | --- |
| `manifest` | `format_version` `template_id` `version` `doc_type` `source_hash` `package_hash` `created_at` |
| `styles` | `name` `style_id` `type`（paragraph / table / character）`based_on` `font`（含东亚字体）`size` `bold` `line_spacing` `space_before/after` `indent` `num_id` |
| `page_setup` | `page_size` `margins` `sections[]`（含分节差异） |
| `numbering` | `abstract_num[]` `num[]` `heading_bindings` |
| `used_styles` | `p_style[]` `tbl_style[]`（含引用次数，用于区分活跃样式与死样式） |
| `outline` | `chapter_tree`（层级 / 标题 / 样式 / 编号）· `allowed_block_types` · `slots[]`（必填 / 可选） |
| `blocks` | `block_id` `kind`（cover / revision / toc / header / table）`locator` `structure` |
| `placeholders` | 待清理的编写说明与占位提示 |
| `fingerprint` | 归一化后的稳定摘要（排除易变 ID） |

**（2）事实包（Fact Bundle）**

| 字段 | 说明 |
| --- | --- |
| `source` | 来源标识（连接器类型 + 实例 + 版本） |
| `kind` | 事实类型，**开放取值**：由领域模型注册表声明（内置示例 `endpoint` / `table` / `field` / `rpc` / `screen` / `requirement` / `asset`；使用方可声明自有类型，如 `testcase` / `procedure` / `clause` / `parameter`）。**引擎不得针对具体 `kind` 分支** |
| `key` | 稳定业务键（如 `GET /api/xxx`、`表名.字段`） |
| `payload` | 结构化内容 |
| `locator` | 原文件定位（文件 + 行 / 路径），用于追溯与报错定位 |
| `verified` | 是否可被现有实现验证；不可验证者强制标注「目标设计 / 待确认」（FR-M3-11） |
| `priority` | 冲突裁决优先级（FR-M1-11） |

**（3）内容 IR（Content IR）**

与格式无关、与模板无关的内容描述。抽象块类型固定为：`heading` `para` `bullets` `numbered` `table` `figure` `screenshot` `trace` `pagebreak` `block_ref`；**领域语义不由块类型承载**，而由体例声明的字段 schema 承载（如"接口清单表"与"测试用例表"同为一个 `table` 单元，仅字段声明不同）。

三条设计约束（与 4.9.1 一一对应，均为可自动检索的判据）：

1. **不得含 OOXML 概念** —— 不得出现 `styleId`、`w:` 前缀、twips、绝对列宽；版式决策一律在渲染层依据契约完成（验收 34）。
2. **不得含领域概念** —— 渲染层不得以"接口""数据表""测试用例"等标签作为分支依据，它只认块类型（验收 42）。
3. **不得含文档类型概念** —— IR 与装配代码中不得出现"概要设计""详细设计"等文档类型名称（验收 42）。

第一条决定内容与版式能否解耦，第二条决定渲染器能否跨领域复用，第三条决定装配器能否跨文档类型复用。**三条中任一条被破坏，通用性即在该处终止。**

**（4）文档类型档案（Doc Type Profile）**

| 对象 | 关键字段 |
| --- | --- |
| `doc_type_profile` | `format_version` `profile_id` `doc_type`（如 `interface_test_plan`）`title` `applies`（适用判据说明：版式来源 / 结构可枚举 / 内容可溯源）`version` |
| `genre` | `chapter_skeleton[]`（层级 / 标题 / 必填槽位）· `allowed_unit_types[]` · `conventions[]`（体例约定：表格无句末句号、图注格式等） |
| `projections[]` | `unit` `for_each`（领域类型）`group_by` `layout`（one_section_per / one_table_per / one_row_per）`fields[]` `columns[]` `order_by` `filter` `required` |
| `bindings` | `template_packages[]`（可换绑的模板包引用）· `rule_sets[]`（门禁规则集）· `terminology_scope`（术语作用域） |
| `fingerprint` | 档案的稳定摘要，用于版本比对与"产出可复现"判定 |

**档案是通用性的载体**：新增一类文档 = 新增一份档案（L1，纯配置）；换甲方模板 = 换 `bindings.template_packages`（L0）。引擎对 `doc_type` 的取值不做任何假设。

**（5）作业与阶段（Job / Stage）**

作业分两级：**编排作业**（`kind = orchestration`，一次构建的顶层单位）与**子作业**（`kind = document`，对应单份文档）。编排作业不执行文档构建，只负责冻结输入、派生并聚合子作业、汇总报告。

| 对象 | 关键字段 |
| --- | --- |
| `job` | `job_id` `parent_job_id`（子作业指向编排作业；编排作业为 null）`kind`（orchestration / document）`project_id` `doc_type`（子作业才有）`status` `child_job_ids[]`（仅编排作业）`created_at` `inputs_hash` `artifact_ids[]` |
| `stage` | **属于子作业**：`name`（ingest / compose / render / refresh / qa）`status` `progress` `started_at` `finished_at` `checkpoint` `error` |
| `event` | `job_id` `stage` `level` `message` `created_at`（供 SSE 推送与审计；可回放） |
| `decision` | 待裁决项：`kind`（qa_finding / template_confirm / dedup / **model_low_confidence**）`target` `options` `chosen` `reason` `operator` |
| `model_call` | 决策点路由记录：`decision_point` `route`（rule / small_model / optional_large_model）`model` `schema_ok` `confidence` `fallback_used` `tokens`（供 7.4 的模型使用面板与成本归集） |

**作业粒度的裁决结论：一个编排作业 + 多个子作业。** 编排作业**不执行文档构建**，只做三件事：冻结输入快照（模板包版本 / 事实源 / 配置版本）→ 按文档族派生等量子作业 → 聚合进度与汇总报告。子作业各自推进完整阶段链、各自产出与裁决。

| 规则 | 内容 |
| --- | --- |
| 状态枚举 | 子作业：queued / running / awaiting_decision / succeeded / failed / canceled；编排作业同源，**多一个 `partial_failure`**（部分子作业成功、部分失败） |
| 聚合来源 | 编排作业状态由服务端聚合子作业状态得出，**界面不得自行推断**（见 7.6.1） |
| 失败隔离 | 子作业失败不回滚、不阻塞其他子作业产物；已完成子作业的产物照常可下载 |
| 续跑粒度 | 两级都可续跑：子作业内按**阶段**续跑；编排作业层面按**子作业**重跑 |
| 产物归属 | 产物挂在子作业上；编排作业只提供聚合视图与「整套下载」 |

**（6）门禁与追溯**

| 对象 | 关键字段 |
| --- | --- |
| `rule` | `rule_id` `category` `severity`（blocker / major / minor）`scope`（doc_type）`expression` |
| `finding` | `rule_id` `severity` `location`（章节 / 段落 / 表格 / 图）`evidence` `suggestion` |
| `waiver` | `finding_id` `reason` `operator` `expires_at`（随报告归档） |
| `report` | `job_id` `summary`（通过 / 未通过 / 豁免）`findings[]` `waivers[]` `artifacts[]` `duration` |
| `trace_edge` | `from`（需求 / 接口 / 表 / 图）→ `to`（章节 / 表格 / 图）+ `kind`（血缘图谱的边） |

`waiver` 与 `trace_edge` 是两个最容易被省掉、却决定系统能否用于正式交付的结构：前者让「人工豁免」可审计，后者让「每一节内容都有来源」可查证。

### 4.8 运行时视图与部署拓扑

**（1）进程拓扑**

```
浏览器（工作台）
   │  HTTP / SSE
   ▼
┌──────────────────┐         ┌──────────────────────┐
│  api 进程         │──读───▶│  作业元数据存储        │
│  FastAPI          │         │  PostgreSQL / SQLite  │
│  鉴权 · 文件 · SSE │◀──写────└──────────────────────┘
└────────┬─────────┘
         │ 投递作业（不在 api 进程内执行）
         ▼
┌──────────────────┐         ┌──────────────────────┐
│  worker 进程池    │──读写──▶│  工作区（文件系统）     │
│  pipeline 阶段机  │         │  uploads / packages / │
│  内核 L0–L4       │◀────────│  jobs/<job_id>/...    │
└────────┬─────────┘         └──────────────────────┘
         │
         └─ 需要 Word 时：调用渲染服务（可选容器），否则降级
```

**（2）四条运行时约束**

| 约束 | 理由 |
| --- | --- |
| **worker 必须独立于 api 进程** | 构建是分钟级任务；跑在 api 进程内会导致重启丢作业、无法水平扩展、无法限制资源占用（对应 3.2 场景 G） |
| **作业状态与阶段 checkpoint 必须持久化** | 服务重启后未完成作业要可识别、可续跑；**续跑粒度是阶段，不是整个作业** |
| **作业之间同项目串行；同一编排作业的子作业可并行** | 不同作业之间共享工作区与模板包版本，并行会引入难以复现的竞争；而同一编排作业的子作业共享**已冻结的输入快照**（模板包版本 / 事实源 / 配置版本），彼此无写冲突，因此可并行（受并发上限约束，见 4.7） |
| **存储分三类、物理隔离** | 作业元数据（可查询 / 可备份）、工作区文件（按保留策略清理）、产物（版本化 / 可下载）——三类生命周期不同，混放会导致清理策略无法执行 |
| **模型服务与 worker 分离** | 模型推理是外部依赖；与构建进程同生命周期会导致「模型服务重启 = 构建失败」。分离后模型不可用时走规则兜底，构建照常完成（见 5.2.4、降级矩阵） |

**（3）工作区布局**

```
workspaces/<project_id>/
├── uploads/                  # 上传的模板与事实源（按保留策略清理）
├── packages/                 # 入库产物：模板包（只读，供多次构建复用）
├── jobs/<job_id>/            # 编排作业：保存输入快照、聚合报告与聚合事件流
│   ├── inputs/               #   冻结的输入快照（模板包版本 / 事实源 / 配置版本 / 哈希）
│   ├── artifacts/            #   汇总报告与整套打包产物
│   ├── events.jsonl          #   聚合事件流（SSE 断线后可回放）
│   └── children/<child_id>/  #   子作业：每份文档一个
│       ├── work/             #     阶段中间态与 checkpoint
│       ├── artifacts/        #     docx / QA 报告 / 渲染目检图 / 事实快照
│       └── events.jsonl      #     子作业事件流
└── decisions/                # 裁决记录（与报告同源，可导出）
```

**（4）降级矩阵**

| 能力 | 依赖 | 缺失时的行为 |
| --- | --- | --- |
| 域刷新（目录 / 页码） | Word COM | 降级为 OOXML 直接重建目录内容，并明确提示「目录需在 Word 中刷新」 |
| PDF 导出 / 逐页目检 | Word COM 或 LibreOffice | 目检降级为结构快照 + 关键页渲染（若可用），报告标注降级原因 |
| LLM 文案与评审 | 模型服务（本地或远端，OpenAI 兼容端点） | **按决策点降级**：文案退化为模板化描述；模型类决策点走规则默认值并标记待确认；门禁与渲染不受影响，**构建不失败**（见 5.2.4） |
| 图表程序化生成 | 本地绘图库 | 只用可用图源，缺口列为门禁 Major 项 |

**（5）首次启动即应成立的最小闭环**

`docker compose up` → 浏览器打开 → 用内置示例数据完成「入库 → 构建 → 门禁 → 下载」。这条闭环是架构是否成立的**可执行证明**：它同时验证了内核零 Web 依赖（示例数据可在无 HTTP 环境跑通）、作业化（构建异步推进）、契约自足（生成期不读模板）与可分发性。P0 的验收以此为准（见第 11 章）。

### 4.9 文档类型无关性（通用性的实现机制）

本节回答一个问题：**为什么换一类文档不需要改引擎？** 答案不是"把代码写通用一点"，而是**三次解耦 + 三层外部数据**。这三条若守不住，所谓通用性会在第二个文档类型到来时立刻瓦解。

#### 4.9.1 三次解耦：把「领域」与「体例」从引擎里挤出去

```
事实源（异构） ──Connector──▶ 领域模型（规范化的业务对象）
                                   │
                          投影规则（Projection Rule）
                                   ▼
                        内容单元（文档中立的语义块）
                                   │
                          渲染策略（模板契约驱动）
                                   ▼
                              docx（OOXML）

  ▲ 领域面：随「被文档化的对象」变化          ▲ 体例面：随「文档怎么写」变化
  └──────────── 引擎面（不变）：调度 · 契约 · 渲染机制 · 门禁机制 · 依赖规则 ────────────┘
```

| 解耦 | 规则 | 违反后的直接后果 |
| --- | --- | --- |
| **① 领域 ← 文档** | 领域模型不得含文档概念（章节、编号、图注、体例） | 同一个领域对象无法投影到第二类文档，「同一事实源多文档类型」不可能成立 |
| **② 内容 ← 领域** | 内容单元不得含领域概念（不得以"接口""数据表"这类标签作为渲染依据） | 渲染层被迫认识领域概念，加一类对象就要改渲染层 |
| **③ 内容 ← 版式** | 内容 IR 不得含 OOXML 概念（`styleId`、`w:` 前缀、twips、绝对列宽） | 即 4.6 决策一 / 五与验收 34 所约束的对象 |

三条规则都是**可自动检索的**：依赖门禁扫描源码与 IR 输出，出现禁用词即失败（NFR-28、验收 42）。**能自动校验的约束才是约束**，否则它会在实现的第一周就被违反。

#### 4.9.2 三层外部数据：领域模型 · 模板包 · 文档类型档案

| 层 | 声明什么 | 载体 | 谁提供 |
| --- | --- | --- | --- |
| **领域模型** | 有哪些领域类型（`endpoint` / `table` / `requirement` / `testcase` / `procedure`…）、每类的字段 schema、标识键、可比较字段、可追溯字段 | 声明式 schema | Connector 作者或使用方 |
| **模板包** | 怎么排：样式契约、结构骨架、版块库、页面设置、表格原型、图片槽位 | docx 原件 + JSON 契约 | 入库流程自动产出（见 4.4） |
| **文档类型档案** | 写什么、怎么写：适用判据、章节骨架、内容单元类型、投影规则、门禁规则集、模板包引用、术语作用域 | YAML 目录 | 使用方（**纯配置，不写代码**） |

**关键：三者正交。** 一个领域模型可被多份档案复用（同一套接口事实，既可出《接口设计》也可出《接口测试方案》）；一份档案可换绑不同模板包（同一体例的公司 A 模板 / 公司 B 模板）；一个模板包也可服务于多个档案。

#### 4.9.3 投影规则：通用装配的真正核心

「接口 → 一接口一节」与「接口 → 一模块一表」这两种体例，在本设计中**不是两段代码，而是同一条投影规则的不同参数**：

```
projection:
  - unit: section            # 内容单元类型（由体例声明）
    for_each: endpoint       # 领域类型（由领域模型声明）
    group_by: tag            # 分组键（领域模型声明的字段）
    layout: one_section_per  # 布局：one_section_per / one_table_per / one_row_per
    fields: [path, method, description, auth]    # 字段映射
    children:
      - unit: table
        for_each: endpoint.parameters
        columns: [name, type, required, desc]
```

| 通用机制 | 作用 | 对应能力 |
| --- | --- | --- |
| `for_each` + `group_by` | 决定"一对多 / 多对一"的装配关系 | 一接口一节 vs 一模块一表 |
| `layout` | 决定呈现形态（节 / 表 / 行 / 图） | 同素材在不同文档中的粒度差异 |
| `fields` / `columns` | 领域字段 → 单元字段的映射 | 不同文档对同一对象的关注点不同 |
| `order_by` / `filter` | 排序与筛选 | 按模块、按优先级、按风险排序 |
| `required` | 未填充即告警 | 槽位完整性 |

**这张表就是"通用性"的具体含义**：新增一类文档时，变化的是这份声明；不变的是执行它的装配器与渲染器。

#### 4.9.4 接入成本分级（通用性的可度量形式）

"支持任意文档类型"必须能被度量，否则无法验收：

| 级别 | 场景 | 需要做什么 | 预期工作量 |
| --- | --- | --- | --- |
| **L0** | 同一文档类型换模板（换甲方、换版本） | 只入库新模板包 | 分钟级 |
| **L1** | 新增文档类型，事实源与领域类型均已支持 | 写一份文档类型档案（体例 + 投影规则） | 小时级，**不写代码** |
| **L2** | 出现新的领域对象（如"测试用例""工艺参数"） | 追加领域模型声明 + 可能的 Connector | 天级，仅声明与适配 |
| **L3** | 出现新的呈现形态（公式、流程图、多栏、嵌套表） | 新增渲染策略插件 | 天级，插件式，不动核心 |
| **L4** | 出现跨领域的新语义维度，现有抽象无法表达 | 修改核心 | **应视为设计缺陷**：先论证能否用 L1–L3 表达，再走 RFC（见 10.7） |

**验收要求**：**L1 必须在不修改引擎代码的前提下完成**，并以"第三类文档类型"实测（验收 44）。若某个新类型必须走 L4，说明前面的抽象有缺口——应先修抽象，而不是就地打补丁。

#### 4.9.5 通用性的验收判据：同源多型

通用性无法靠"声称支持"证明，只能靠**同一份事实源产出多种文档类型**证明：

| 判据 | 说明 |
| --- | --- |
| **同源多型** | 同一事实包分别产出结构形态不同的两类文档，且事实逐项一致、样式各自保真 |
| **零代码** | 上述两种产出使用同一份引擎版本，差异只体现在档案与模板包上 |
| **可交换** | 档案与模板包打包后可交给第三方，第三方在其环境中复现同样的产出 |

这三条直接成为 10.10（示例资产）与第 11 章验收 42–45 的输入。

## 5. 技术架构与 Agent 设计

第 4 章定义**系统的结构与边界**（分层、模块、依赖、数据模型、运行时拓扑），本章定义**用什么技术实现它，以及 Agent 在其中扮演什么角色**。两章刻意分开：结构应当与具体技术选型无关。

### 5.1 技术选型

| 组件 | 选型 | 理由 |
| --- | --- | --- |
| Agent 编排 | **OpenAI Agents SDK**（`openai-agents`，MIT，Python ≥ 3.10） | 官方生产级多 Agent 框架：`@function_tool` 把确定性能力封装为工具、`handoffs` 表达 Agent 协作、`guardrails` 做合规拦截、内建 tracing；模型无关（支持 100+ LLM），不锁定供应商 |
| 契约与模型 | Pydantic v2 + JSON | 模板契约需强类型校验；与 SDK 的 `output_type` 结构化输出天然契合，避免自由文本在流水线里漂移 |
| OOXML 操作 | python-docx + lxml 直改 | 大量操作 python-docx 无 API（`numbering`、`tblStylePr`、`sdt`、`wp:extent`），必须下沉到 lxml |
| 依赖规则落地 | import-linter + 自定义 AST 检查 | 4.6 的模块依赖规则必须**可自动校验**，否则模块边界会在实现推进中被逐步侵蚀（呼应 OS-06） |
| 渲染与 QA | Word COM（可选）+ PyMuPDF | 域刷新与 PDF 导出依赖 Word；无 Word 环境自动降级 |
| 能力暴露 | MCP Server（**后置**，不在本期范围） | 对外以 MCP 暴露模板库与事实源，供外部 Agent 调用；本期 Agent 在服务端进程内直接调用，先不引入协议层 |
| CLI | Typer（**后置**，仅作为引擎的薄壳入口） | 本期不作为交付形态；但引擎内核必须可被独立调用，为将来 CLI / 库形态留出接口 |
| Web 服务端 | FastAPI + Pydantic v2（复用契约模型）+ SSE | 与契约模型同栈，避免二次建模；SSE 足以推送作业进度，不必引入 WebSocket 的复杂度 |
| 作业与状态 | 作业持久化（PostgreSQL 或 SQLite）+ 独立 worker | 构建是分钟级长任务，必须异步化且状态可持久化，支持重启续跑（见 3.2 场景 G） |
| 前端 | 组件化框架（按团队熟悉度选型） | 界面以表单、表格、差异对比、报告查看与目检图为主；业务判断一律留在服务端 |
| 分发 | Docker 镜像（单容器 / Compose，自部署优先） | 模板属甲方资产，服务端部署位置与显式授权的模型端点共同决定数据流向（见 10.11） |
| 上游依赖策略 | **薄适配层 + 版本区间锁定** | `openai-agents` 处于 0.x，破坏性变更频繁；核心链路不直接依赖上游对象模型，便于替换与稳定（见第 13 章） |

**为什么选 Agents SDK 而不是直接调 LLM API**：本系统的核心难点不是"生成一段文字"，而是**多阶段、可中断、需审计、要拦截**的长流程。SDK 恰好提供了 handoffs（阶段流转）、guardrails（写盘前拦截）、RunState（断点恢复）、tracing（决策留痕）四件套，这些自己实现成本极高且容易做错。

### 5.2 模型策略：配置模型逐点实测与分级降级

**目标**：Agent 使用显式配置的 OpenAI 兼容模型端点，按逐决策点的真实评测决定接管范围。**不要求固定参数量、量化方式或本地部署；模型不是运行前提。** 本轮真实验收使用当前 `.env` 指定的模型；更换模型或配置后须重新评测，不能沿用身份不匹配的基线。

**必须保留的约束：**

1. **数据边界**（10.11）—— 默认关闭模型；仅向显式配置且获使用方授权的端点发送声明范围内的必要、脱敏内容，禁止隐式云端回退与 tracing 外发；
2. **可复核**（10.9）—— 留存模型标识、样本与路由配置指纹、输出校验及降级结果；确定性回归使用冻结结果或回放，真实模型不承诺逐字复现；
3. **成本可控** —— CI 与常规回归不调用真实模型；真实验收单独记录用量，关闭模型时调用数为 0；
4. **能力以实测为准** —— 参数量、部署位置和 HTTP 成功均不能替代任务正确率；未达标决策点走规则或人工。

#### 5.2.1 模型服务的三类失败模式

| 短板 | 具体表现 | 后果 |
| --- | --- | --- |
| 结构化输出不稳 | 不按 schema 输出、漏字段、夹杂解释性文字、JSON 截断 | 流水线中断，或产出难以被判定的半成品 |
| 工具选择易错 | 工具数量多、描述长时选错工具，或编造不存在的参数 | 调错能力、污染产物 |
| 多跳推理弱 | 需要"先查契约、再判重、再落位"的连续推理时跳步或遗漏前置条件 | 判定不可靠，且错误难以复现 |

**共同的兜底事实**：这些问题可能出现在任何模型上，不能凭模型规模推断可靠性。系统必须约束选择空间，并通过逐点评测与失败降级保障质量。

#### 5.2.2 六条设计对策

| 对策 | 机制 | 落点 |
| --- | --- | --- |
| **决策面收窄** | 每个 Agent 只做一类决策；单次调用只回答一个问题；工具数 ≤ 7 且参数扁平、无嵌套；不设"顺带再做一件事"的复合工具 | 5.4、5.5 |
| **结构化输出强制** | 全部 Agent 输出按 `output_type` 对应的 Schema 校验；按端点能力启用 JSON Schema 或受限解码。不支持时使用 JSON 对象与字段约束，结合校验、有限重试和规则兜底，不能跳过校验 | 5.1、NFR-24 |
| **候选注入代替自由生成** | 不要求模型"想出"答案：先由确定性代码算出候选集（可选样式列表、候选章节、候选接口、候选枚举值），模型只做**选择**。选择远比生成可靠 | 5.4 Agent 清单 |
| **规则优先兜底** | 每个决策点都必须有规则默认值；模型不可用、输出校验失败、置信度缺失或低于阈值时，默认走规则值并标记**待确认**送入裁决队列，**不阻断构建** | 5.3、NFR-26、验收 39 |
| **上下文受控** | 不投喂完整契约与全量事实；由检索按决策点裁剪上下文（契约片段 + 命中事实 + 体例摘录），单次决策上下文有明确上限 | NFR-25 |
| **可评测可回归** | 建立**任务级能力基线**（逐决策点的通过率）；未达阈值的决策点**不交给模型**，继续走规则或人工 | 10.9、验收 41 |

#### 5.2.3 决策点分级：哪些交给模型、哪些绝不

**每个决策点都必须在设计阶段显式归类**，避免实现时未经准入扩大模型的接管范围。

| 决策点 | 归属 | 理由 |
| --- | --- | --- |
| 版式决策（标题样式、列宽、版心、分页、编号） | **规则** | 契约里已有确定答案，问模型只会引入不确定性（呼应 4.4.4"查契约"） |
| 门禁判定（样式 / 版式 / 术语 / 完整性 / 追溯） | **规则** | 能写成断言，且必须可复现（呼应 5.3 原则） |
| 模板结构解析、契约生成、指纹计算与版本比对 | **规则** | 需逐字段精确，禁止模型参与 |
| 几何计算（图片等比缩放、表格宽度归一） | **规则** | 与语义无关的确定性问题 |
| 变更点的**语义**判重（路径不同、功能相同） | **配置模型** | 需要语义理解；但输出被限制为"重复 / 不重复 + 理由"的封闭选择 |
| 章节内容落位（插入点已给出候选） | **配置模型** | 从候选清单中选择，不做自由创作 |
| 体例冲突的裁决建议 | **配置模型** | 只出建议，最终由人裁决 |
| 文案生成与改写 | **配置模型（可选）** | 关闭后退化为模板化描述，链路不受影响 |
| 文档评审（缺失 / 薄弱 / 矛盾） | **配置模型（可选）** | 输出结构化结论，不作为阻断依据 |
| 事实源冲突裁决 | **人工** | 属业务判断，模型不参与（呼应 FR-M1-11） |

这张表同时是**能力路由**的定义。为兼容既有配置，保留 `rule / small_model / optional_large_model / human`：分别表示规则 / 配置模型 / 可选模型 / 人工；模型档名称是历史路由标识，**不表示参数量或部署位置**。运行时按声明与基线准入路由，界面可查看实际路径（见 7.1.2）。

#### 5.2.4 三条硬约束

1. **模型不可用必须可运行。** 关闭模型后全链路仍产出合规文档（NFR-13 的一等公民，验收 18/39）。任何"没有模型就跑不动"的设计都视为缺陷，而非配置缺失。
2. **升级模型不得改契约。** 模型与提示词都封在**薄适配层**内；换模型、换版本、换推理服务只允许改 instructions 与适配层，不得触碰契约、渲染与门禁（呼应 NFR-14、5.1 上游依赖策略）。
3. **不允许把"换个更聪明的模型"当作解决方案。** 遇到判定不可靠时，首选把该决策点**降级为规则或候选选择**，而不是换更大的模型。这条是防止本项目退化成一个昂贵提示词工程的前提。

**置信度缺失的准入约束**：缺失值代表未知，默认规则兜底并标记待确认。若引入独立校验或人工确认作为替代准入依据，必须显式配置、留存依据并通过逐点真实评测；不得捏造置信度，也不得仅把阈值置 0 就宣称已达标。

#### 5.2.5 接入方式与部署

| 项 | 约定 |
| --- | --- |
| 接入协议 | **OpenAI 兼容端点**（`base_url` + `model` + 密钥），支持本地、内网或显式授权的外部服务；调用范围遵守 10.11 |
| 结构化输出 | 探测 JSON Schema / 受限解码支持情况；不支持时使用 JSON 对象与字段约束，并降级为"校验 + 重试 ≤ N 次 + 规则兜底"；设置页如实展示能力 |
| 提示词风格 | 短句、扁平结构、单一目标；每个工具描述 = 一句动作 + 参数说明 + 一个最小示例；避免长 system prompt 与多层嵌套要求 |
| 部署关系 | 模型服务与构建 worker **分离部署**：模型服务重启不得导致构建失败；模型关闭时本应用不发模型请求、不启动推理进程，不承诺释放共享模型服务的资源（呼应 4.8 降级矩阵） |
| 成本与用量 | token 用量按决策点、Agent 与阶段归集；确定性模式下模型调用数为 0（NFR-18） |

### 5.3 Agent 与确定性代码的边界（最重要的一条）

| 交给 Agent（LLM 决策） | 必须是确定性代码 |
| --- | --- |
| 章节内容规划与落位判定 | **OOXML 读写**（样式、编号、表格、图片、域） |
| 体例冲突的裁决建议 | **模板解析与契约生成** |
| 文案生成与改写 | **模板深拷贝与注入** |
| 变更点的语义去重（路径不同但功能相同） | **分页 / 列宽 / 图片的几何计算** |
| 文档评审（缺失 / 薄弱 / 矛盾） | **门禁规则判定**（能写成规则的绝不问 LLM） |
| 漂移影响面分析 | **指纹计算与版本比对** |

**原则：能写成规则的绝不交给 LLM；必须精确读写 OOXML 复杂部件的绝不交给 LLM。** Agent 决定"做什么"，代码负责"精确地做"。

理由：LLM 操作 OOXML 失败率高且不可复现，而文档交付要求"样式零偏差"与"确定性构建"。实践中只要出现一次 `tblStylePr` 条件格式的误判，整份文档的表头样式就会失效。

### 5.4 Agent 清单

| Agent | 职责 | 主要工具 | handoff 去向 |
| --- | --- | --- | --- |
| **Curator** 模板馆员 | 模板入库解析、契约生成、指纹与版本比对 | `template_parse` `contract_build` `block_index` `fingerprint_diff` `registry_put` | → Architect |
| **Architect** 文档架构师 | 读结构骨架与事实源，规划章节内容清单与落位 | `outline_read` `source_query` `trace_map` `slot_plan` | → Composer |
| **Composer** 内容撰写 | 生成章节内容 IR（含文案），套用术语变量 | `content_ir_build` `glossary_apply` `endpoint_section` `table_section` | → Renderer |
| **Renderer** 版式落地 | 调确定性渲染工具把 IR 落成 docx | `render_inject` `pagination_apply` `figure_place` `toc_refresh` | → Inspector |
| **Inspector** 质量审查 | 门禁校验、体例评审、漂移检测，输出返工清单 | `qa_run` `style_audit` `drift_check` `render_spotcheck` | → Composer（不合格返工） |

```
Curator ──▶ Architect ──▶ Composer ──▶ Renderer ──▶ Inspector
                              ▲                        │
                              └────── 不合格返工 ───────┘
```

设计约束：

1. 每个 Agent 单一职责，**不设"万能 Agent"**；
2. Agent 数量克制在 5 个，新增能力优先加工具而非加 Agent；
3. 每个 Agent 的 `output_type` 用 Pydantic 模型约束结构化输出；
4. handoff 是**显式**的阶段流转，不用提示词暗示。

确定性能力全部封装为 `@function_tool`，按层归属：

| 工具组 | 工具 | 归属模块 |
| --- | --- | --- |
| 模板 | `template_parse` `contract_build` `block_index` `fingerprint_diff` `registry_put` `registry_get` | M2 |
| 事实源 | `openapi_load` `ast_extract` `orm_introspect` `proto_parse` `xlsx_read` `asset_index` | M1 |
| 内容 | `content_ir_build` `glossary_apply` `endpoint_section` `table_section` `figure_render` | M3 |

| 门禁 | `qa_run` `style_audit` `structure_audit` `layout_audit` `glossary_audit` `trace_audit` `render_spotcheck` | M5 |

1. 工具输入输出必须是**可序列化的 Pydantic 模型**；
2. 每个工具必须定义**明确的失败返回格式**（供 Agent 重试或降级），不允许抛裸异常给模型；
3. 工具签名保持稳定，避免提示词与调用失配；
4. 高危工具（写盘、覆盖、删除、刷新域）标注需人工审批。

### 5.6 Guardrails

| 类型 | 位置 | 拦截内容 |
| --- | --- | --- |
| 输入护栏 | 用户指令进入前 | 要求编造未经事实源支撑的内容；要求修改模板原件；要求绕过门禁 |
| 工具输入护栏（审批前） | 高危工具调用前 | 未确认的写盘/覆盖/删除；目标路径越界；作用域外文件 |
| 输出护栏 | **写盘前** | 契约违规（样式层被改、引用 styleId 不存在）、占位残留、术语禁用词命中、图片越界 |

关键点：**输出护栏必须在写盘前拦截**，而不是生成完再回查——否则污染工作区与产物目录。

### 5.7 会话、断点与可观测

1. **Sessions**：保留跨轮上下文（针对同一模板库的连续操作）。
2. **RunState 断点恢复**：构建是长流程（入库 → 编排 → 渲染 → 刷新 → 门禁），必须支持中断后从快照恢复，避免重跑全链路。
3. **Tracing**：启用内建 tracing，按 `run_id` 追踪每个 Agent 的决策与工具调用；token 用量按 Agent 与阶段归集，用于成本分析。
4. **决策留痕**：Agent 的每条自动决策（跳过某接口、判定功能重复、豁免某规则）连同理由写入构建报告，满足"可解释"原则。

### 5.8 领域知识承载：AGENTS.md

仓库根目录提供 `AGENTS.md`，向 Agent 声明项目结构与约定（SDK 原生支持读取）：文档类型与体例约定、术语规范、门禁规则摘要、模板包格式、贡献者调整 Agent 行为的入口。

这样"体例知识"从个人经验变成仓库里可评审、可版本化的资产。

### 6.2 M2 模板库与文档类型档案（Template Registry）

**设计要点**：模板解析从生成流程中抽离，改为独立的**入库流程**。模板只需解析一次，结果固化为模板包；生成阶段只读模板包契约，**不再现场解析或对比模板**。

同一思路适用于**文档类型档案**：体例与投影规则写好一次、登记入库，生成期只读档案（见本节（4））。模板包解决「怎么排」，档案解决「写什么、怎么写」，二者都是可复用、可交换的资产（见 4.9.2）。

## 7. Web 端信息架构

本章回答三个问题：**使用者在哪里做每件事**（导航与页面归属）、**每件事需要看到什么、填什么**（字段与状态）、**做完之后如何知道成了、错了、下一步是什么**（反馈与续跑）。

它不是界面美化方案，而是把第 2–6 章的约束**翻译成界面的「可做与不可做」清单**。范围限定为信息架构——导航结构、页面清单、页面字段、操作、状态与交互模式，以及页面 ↔ 后端能力的映射；视觉稿、组件实现与 HTTP 接口签名不在本章范围。

### 7.1 设计约束

#### 7.1.1 从总体架构与功能需求继承的硬约束

信息架构不能自由发挥，以下六条直接限定界面形态：

| 约束 | 出处 | 对界面的具体要求 |
| --- | --- | --- |
| 界面只做呈现、收集与裁决 | NFR-22、2.5 | 不得出现任何直接改文档的操作入口（改样式、改列宽、改 XML）。能改的只有**配置**与**裁决** |
| 长任务必须作业化 | FR-M7-03/04/15、3.2 场景 G | 任何构建都不得同步等待；进度以**阶段**为单位呈现；必须以**子作业**为单位隔离失败，可取消、重试、从失败阶段续跑 |
| 确定性模式是默认路径 | NFR-13、10.3 OS-14 | 默认界面不出现 LLM 相关设置；LLM 开关在设置内且**默认关闭**；关闭状态在项目总览可见 |
| 数据边界由部署与授权端点决定 | 10.11 | 部署位置、模型调用边界与「什么会离开本机」必须在首屏可见；产物保留策略与一键清理必须有一级入口 |
| 一切人工判断可追溯 | NFR-15、FR-M5-14 | 裁决必须收集**理由 + 责任人**；只提供"接受 / 改配置 / 豁免"三种规范动作 |
| 对外契约稳定 | 10.6 | 前端路由与关键操作路径定为 **Beta**：可调整，但不得在未告知的情况下让既有路径失效 |

一条由此推出的界面纪律：**界面上每一个"能改的东西"，都必须能对应到配置文件里的一行。** 凡是只能通过界面点出来、落不到配置的改动，一律不做——否则配置驱动（FR-M7-08）会退化为"界面状态"。

#### 7.1.2 模型准入与降级对界面的两条要求

模型按配置与逐点基线接管（见 5.2），界面须满足两条要求：

1. **模型能力必须可见** —— 模型是否启用、接的是哪个端点、受限解码是否生效、每个决策点走的是规则还是模型、哪些项因基线未达标或置信度缺失 / 低置信而退回默认值，都要能查到；调用边界与降级依据必须可排查。
2. **低置信项必须可裁决** —— 低置信走了规则默认值的项，必须进入裁决队列（P12），而不是静默采用。界面是"模型不确定"这一事实的唯一出口。

### 7.2 用户与任务分层

#### 7.2.1 角色 × 任务矩阵

| 角色 | 主要任务 | 高频页面 |
| --- | --- | --- |

#### 7.2.2 任务频次决定入口位置

这是本章最实用的一条分层依据 —— **入口位置由使用频次决定，而不是由功能归属决定**：

| 频次 | 任务 | 入口位置 |
| --- | --- | --- |
| **高频**（每天，几秒内要看到结果） | 看作业跑没跑完、处理待裁决、拿产物 | **顶部全局区**（作业指示器 / 待裁决徽标） |
| **中频**（每次交付一轮） | 入库模板、配置清单、发起构建、审阅报告 | **项目内左侧导航** |
| **低频**（换版、换项目、排查） | 模板版本对比、新增事实源连接器、存储清理、模型与 LLM 开关 | **全局库页 / 设置页** |

推论：**跨项目的东西进顶部，项目的东西进左侧，一次性的东西进向导。** 例如"模板入库"虽然属于模板库，但它是线性的多步流程且不需要常驻，因此做成向导（P05）而非导航项。

| `/projects/:pid/jobs` | P08 | 发起与管理作业 | 作业提交 / 列表 / 取消 | Beta |
| `/projects/:pid/jobs/:jid` | P09 | 看进度、看失败、局部续跑 | 作业详情 / 事件流（SSE）/ 续跑 | Stable（作业状态与阶段枚举） |
| `/projects/:pid/jobs/:jid/report` | P10 | 逐条裁决未通过项 | 报告查询 / 裁决提交 | Beta |
| `/projects/:pid/artifacts` | P11 | 取产物、做对比 | 产物列表 / 对比 / 复现包导出 | Beta |
| `/projects/:pid/drift` | P14 | 发现文档过期 | 事实快照比对 | Beta |

> 稳定度按 10.6 分级：**路径本身是 Beta**；但 P09 依赖的「作业状态与阶段枚举」是 **Stable**——它同时被 API、报告与第三方集成消费，改名或删除必须走弃用流程（允许新增取值，例如 `partial_failure`）。

#### 7.3.4 导航规则

1. **深度不超过三层**：根 → 项目 → 对象（作业 → 报告 属同一对象的页签，不计为一层）。
2. **面包屑必须能回到列表页**，且返回时**保留筛选与排序**（否则高频复核场景会反复重设）。
3. **不出现"当前项目"歧义**：所有项目内页面必须在面包屑处显示项目名与项目 ID 后四位。
4. **有且只有一个"当前作业"焦点**：右上作业指示器指向最近一个活动作业，历史作业只能从 P08 进入。
5. **待裁决徽标常驻**：只要存在未处理裁决，徽标就不可隐藏——这是防止"漏裁决导致定稿带病"的唯一机械保障。
6. **编排作业与其子作业共用一个作业号命名空间**：子作业以 `父作业号-序号` 呈现，避免出现两套编号习惯。

### 7.4 页面规格

每个页面按固定七项描述：**目的 / 入口 / 关键区域 / 关键字段 / 主要操作 / 状态与空态 / 非目标**，并标注对应需求编号。字段列的是**首版必须有的最小集**，非全集。

#### P04 模板包详情

**目的**：让使用者核对"系统从模板里读出了什么"，并看清版本之间改了什么。**这是整个系统可信度的核心页面** —— 模板解析一旦有偏差，后面全错。

**入口**：`/templates/:tid`（默认最新版本，可切换）

**关键区域（页签）**

| 页签 | 内容 |
| --- | --- |
| **概要** | manifest 全部字段（文件编号 / 版本 / 文档类型 / 入库时间 / 包哈希 / 来源文件名）、完整性校验结果、引用该包的作业与文档 |
| **样式契约** | 样式表（名称 / styleId / 类型 / 基于 / 字体含东亚字体 / 字号 / 加粗 / 行距 / 段距 / 缩进 / 编号绑定）；**活跃样式与死样式分组**；直设格式告警 |
| **页面设置** | 纸张、页边距（分节差异分列标注）、推导出的版心宽高 |
| **结构骨架** | 章节树（层级 / 标题 / 样式 / 编号）+ 每章允许的块类型 + 槽位（必填 / 可选，未填高亮） |
| **版块索引** | cover / revision / toc / header / table 列表（block_id / 类型 / 定位 / 结构摘要 / 是否可跨模板引用） |
| **编号体系** | abstractNum / num 列表、层级缩进、标题样式绑定的 numId |
| **待清理占位** | 编写说明与占位提示清单（文字 / 位置 / 拟用清理规则） |
| **指纹** | 指纹摘要、与上一版本的差异入口 |

**主要操作**：切换版本、版本对比、标记废弃（需理由）、导出模板包、重新入库

**状态与空态**：无历史版本 → 对比入口禁用并说明原因；完整性校验未过 → 顶部红条并列出未过项。

**非目标（这条很重要）**：**不提供"直接编辑契约"的功能。** 修正方式只有两条——编辑 `overrides` 配置后重新解析，或修正模板原件后重新入库。理由见 4.4.2：契约是**索引**，原件才是渲染材料；一旦允许手工改契约，契约就会脱离原件，"生成期只查契约"的前提立刻失效。

**对应需求**：FR-M2-01~07、FR-M2-18、FR-M2-19、FR-M2-20

#### P05 模板入库向导

**目的**：把"解析一次 + 人工确认"的完整过程收敛成一条线性、可中断、可回执的流程。

**入口**：`/templates/import`

**五步流程**

| 步骤 | 界面内容 | 关键字段 / 操作 |
| --- | --- | --- |
| **1 上传** | 拖拽区 + 文件清单 + 逐份的属性表单 | 文件（docx，可多选）、文档类型、文件编号、版本、备注；上传即校验：类型 / 大小 / 可解析性 / 宏检测 |
| **2 解析** | 阶段进度：解包 → 样式层 → 编号 → 结构 → 版块 → 槽位 → 指纹；每阶段完成后显示产出摘要 | 取消；失败时定位到阶段与原因 |
| **3 入库报告** | 契约摘要卡（样式数 / 活跃样式数 / 编号层级 / 表原型数 / 槽位完成度）、结构骨架树、版块索引、占位清单、**待确认项**、完整性校验结果 | 展开查看、跳转到对应页签 |
| **4 待确认项裁决** | 逐条列出低置信项及候选：样式别名映射 / 版块候选定位 / 表格用途推断 / 编号绑定 | 每条给出候选与**判定依据**；支持"全部接受推荐"；结果写入 overrides 配置 |
| **5 登记** | template_id / version / 文档类型 / 包哈希预览 | 确认登记；回执显示模板包路径 + 后续可做（在项目中使用 / 版本对比） |

**状态与空态**

- 解析失败：给出可执行动作——"仅登记原件、稍后重试解析"（不阻塞流程）。
- 待确认项为 0：跳过第 4 步，直接登记（不制造无意义的人工步骤）。
- 重复登记（同 template_id + version）：提示选择新版本或覆盖，不静默覆盖。

**非目标**：不做自由编辑的样式映射表（复杂场景走 overrides 文件）；不做模板内容可视化编辑。

**为什么把"待确认项"单列一步**：解析置信度不可能总是 100%，但**人工确认必须是一次性的、有据可查的**。把它塞进报告页让用户自己找，结果是没人看；把它做成一步，才可能被真正执行。

**对应需求**：FR-M1-01、FR-M1-03、FR-M2-01~04、FR-M2-12~15

#### P09 作业详情

**目的**：看清"这次构建整体到哪一步、哪一份文档卡住了、怎么只重跑它"。

**入口**：`/projects/:pid/jobs/:jid`（编排作业与其子作业共用本页，按 `kind` 切换呈现）

**关键区域**

| 区域 | 内容 |
| --- | --- |
| **子作业矩阵**（仅编排作业） | 每份文档一行：文档名 / 状态 / 当前阶段 / 耗时 / 产物 / 操作（进入子作业详情、单独重跑）；失败项标红，顶部给出"仅重跑失败子作业" |
| 阶段时间线（子作业内） | ingest → compose → render → refresh → qa；每阶段显示状态、起止时间、耗时、产出、是否留有 checkpoint |
| 实时事件流 | 分级（info / warn / error）、可暂停自动滚动、可搜索、可下载 `events.jsonl`；编排作业显示聚合事件，可切换到某子作业的事件流 |
| 输入快照 | 本次使用的模板包版本、事实源、配置版本、输入哈希（可展开核对） |
| 失败面板 | 错误定位（阶段 + 文件 + 位置）+ 三个动作：重试本阶段 / 从本阶段续跑 / 从头重跑；明确标注"已完成阶段不会重跑" |
| 模型使用面板 | 本次作业的决策点路由结果：哪些用了模型、哪些走了规则默认值、哪些因低置信待确认（见 5.2、7.1.2） |
| 裁决需求面板 | 若阶段产出待裁决项，作业状态变为 `awaiting_decision`，提供"去裁决"入口 |
| 产物快捷区 | 文档 / 报告 / 目检图直达 |

**状态与空态**

- 服务在构建中重启后回到本页：顶部提示"该作业因服务重启中断，可从阶段 X 续跑"（对应验收 28）。
- 编排作业存在失败子作业：显示 `partial_failure` 并突出"已完成子作业的产物不受影响"，明确失败隔离。
- 事件流断线：自动重连并从上次游标续推；不允许静默停止推送（长任务里"界面卡住"和"任务卡住"无法区分，是最糟糕的体验）。

**非目标**：不在作业详情里编辑内容；不做阶段间的可视化编排；**不在界面上自行推断编排作业的聚合状态**（聚合规则唯一来源是服务端）。

### 7.5 跨页面交互模式

以下四种模式被多个页面复用，必须先定义再实现，否则每个页面各写一套。

#### 7.5.1 作业指示器（全局）

| 项 | 约定 |
| --- | --- |
| 位置 | 顶部栏右侧，常驻 |
| 内容 | 编排作业：`子作业 3/5 完成 · 当前：详细设计 · 渲染阶段`；子作业：阶段名 + 阶段内进度 + 耗时 |
| 交互 | 点击进入 P09 |
| 为什么不可隐藏 | 长任务若没有指示器，使用者会**重复提交**——这是作业化系统最常见的资源浪费 |

#### 7.5.2 待裁决徽标（全局）

数量 = 未处理裁决项。**不可隐藏**：漏裁决会直接导致"带病定稿"，这是本项目最不希望发生的交付事故。

#### 7.5.3 差异对比器（三种形态，一套视觉语言）

| 形态 | 用在哪里 | 呈现方式 | 关键要求 |
| --- | --- | --- | --- |
| **契约对比** | P04 模板版本差异 | 树形字段级 diff，按 styles / page_setup / numbering / outline / blocks 分区 | 每个变更项标注"影响面"（会影响哪些版式决策） |
| **结构快照对比** | P11 两次产出对比 | 表格：段落数 / 样式引用 / 表格行列 / 图片尺寸 / 分页位置 | 只比结构，不比字节（见 10.9） |
| **文本对比** | P11 产出文本差异 | 行级 diff | **必须先归一化易变标识**，并在界面明确标注"已剔除目录书签 ID 等假差异" |

#### 7.5.4 渲染目检器

统一组件，出现在 P10（定位联动）与 P11（产物审阅）：

- 缩略图墙 → 点击放大 → 左侧章节树定位；
- 问题标注层：图片越界、占位残留、表格越界，可切换显示；
- 对照模式：左侧模板原页面、右侧产出页面（这是"保真度"最直观的证据形态）；
- 无 Word 环境时：显式标注降级，只展示结构快照。

#### 7.5.5 列表约定

默认排序、筛选可保留（返回不丢）、分页显示总数、**空态必须给出下一步动作**、危险操作用文字标签而非仅颜色区分。

#### 7.5.6 高危操作二次确认清单

| 操作 | 确认内容 |
| --- | --- |
| 标记模板包废弃 | 影响面：哪些文档引用了它 |
| 清理产物 | 列出将被删除的对象与数量 |
| 关闭模型后重新构建 | 说明文案将退化为模板化描述、低置信决策点改走规则默认值 |
| 覆盖同 template_id + version | 明确是新版本还是覆盖 |
| 批量接受裁决推荐 | 列出条目数，不可跨项目跨类型 |

### 7.6 状态与反馈

#### 7.6.1 作业状态机（编排作业 + 子作业）

作业分两级：**编排作业**（一次构建的顶层单位）与**子作业**（对应单份文档）。二者状态枚举同源，编排作业多一个聚合态 `partial_failure`。

```
【编排作业】                              【子作业 ×N（每份文档一个）】
        ┌────────┐  投递   ┌─────────┐          ┌────────┐  投递   ┌─────────┐
发起 ─▶ │ queued │ ─────▶ │ running │ ──派生──▶│ queued │ ─────▶ │ running │
        └────────┘        └────┬────┘          └────────┘        └────┬────┘
                               │                                      │
                               │                       产出待裁决项 ───┼──▶ awaiting_decision ──裁决完成──▶ running
                               │                                      │
                               │                       失败 / 异常 ────┴──▶ failed ──┬─ 重试本阶段 ─▶ running
                               │                                                 ├─ 从阶段续跑 ─▶ running
                               │                                                 └─ 从头重跑  ─▶ queued
                               │
                               ├── 全部子作业 succeeded 且无待裁决 ──▶ succeeded
                               ├── 存在待裁决（其余已完成）       ──▶ awaiting_decision
                               ├── 部分 succeeded、部分 failed    ──▶ partial_failure
                               ├── 全部 failed                    ──▶ failed
                               └── 用户取消                        ──▶ canceled
```

| 状态 | 归属 | 界面呈现 | 可用动作 |
| --- | --- | --- | --- |
| `queued` | 两者 | 等待中（含排队位置） | 取消 |
| `running` | 两者 | 阶段时间线 + 实时事件流；编排作业额外显示子作业矩阵 | 取消、查看阶段产出 |
| `awaiting_decision` | 两者 | 醒目提示 + "去裁决" | 裁决、取消 |
| `succeeded` | 两者 | 结论卡 + 产物入口 | 下载、对比、定稿 |
| `failed` | 两者 | 失败面板（定位 + 原因） | 重试本阶段 / 从阶段续跑 / 从头重跑 / 导出复现包 |
| `partial_failure` | **仅编排作业** | 子作业矩阵中标红失败项 + "仅重跑失败子作业" | 重跑失败子作业、进入失败子作业详情 |
| `canceled` | 两者 | 灰显 + 取消时间 | 重新发起 |

**三条规则**：

1. **聚合状态唯一来源是服务端** —— 界面不得自行推断（否则枚举新增时前端会出现歧义，见 P09 非目标）。
2. **失败隔离** —— 子作业失败不回滚、不阻塞其他子作业的产物；编排作业也不因单个子作业失败而丢弃已完成产物。**这正是选择"一个编排作业 + 多个子作业"这一粒度的理由**（决策见 4.7）。
3. **允许新增取值** —— 状态与阶段枚举属 Stable，但允许新增；前端不得对未知取值直接报错，需降级呈现为"未知状态（请升级界面）"。

#### 7.6.2 模板包状态

`解析中 → 已登记 → （可选）已废弃 → 被替代`

废弃不等于删除：已废弃的模板包仍可被历史产物引用追溯（FR-M2-20）；新作业不得再选择已废弃版本。

#### 7.6.3 门禁级别的呈现规则

| 级别 | 颜色角色 | 是否阻断定稿 | 附加要求 |
| --- | --- | --- | --- |
| Blocker | 危险色 | **是** | 必须显示"为什么阻断"与可执行动作 |
| Major | 警告色 | 否 | 可豁免，豁免需理由 |
| Minor | 中性色 | 否 | 仅提示，可批量接受 |

**颜色不作唯一区分**：每处都用文字标签（Blocker / Major / Minor）标注——这是无障碍要求，也避免色弱使用者误判。

#### 7.6.4 三类反馈

| 类型 | 约定 |
| --- | --- |
| 加载 | 骨架屏，不用全屏遮罩（长任务页面若被遮罩挡住，用户无法判断是"在跑"还是"卡死"） |
| 空态 | 必须包含"下一步动作"，不允许只写"暂无数据" |
| 错误 | 三段式：发生了什么 + 影响什么 + 可以做什么。阶段级失败**不得只显示"失败"** |

#### 7.6.5 通知

站内作业完成提示（可开关）。**不做外发通知**（邮件 / webhook 后置）——数据边界优先（10.11）。

#### 7.6.6 文案与无障碍约定

- 操作按钮使用动词（"发起构建"而非"确定"）；
- 危险操作按钮不使用与常规操作相同的措辞；
- 所有表格可全键盘操作，焦点可见；
- 术语与文档正文保持一致（术语表是唯一来源，界面上不出现第二套叫法）。

| P04 模板包详情 | 契约查询、指纹比对、包完整性校验 | `registry` |
| P05 入库向导 | 上传校验 → 入库作业 → 登记回执 | `ingest`（校验）+ `registry` |
| P06 事实源 | 事实源 CRUD、试接入、条目查询 | `ingest` |

| P08 作业列表 | 作业提交（编排 + 派生）、列表、取消、前置检查 | `pipeline` |

### 7.8 非目标（明确不做）

| 不做 | 理由 |
| --- | --- |
| 可视化拖拽编排文档结构 | 配置以表单表达即可；拖拽会带来巨大前端成本，且与"配置驱动"冲突 |
| 在线编辑 docx / 协同批注 | 与"模板保真 + 确定性构建"模型冲突；编辑应回到事实源或配置 |
| 直接编辑模板契约 | 会让契约脱离原件，破坏"生成期只查契约"的前提（见 P04 非目标） |
| 一键忽略全部门禁项 | 门禁是唯一的质量底线，必须逐条留痕 |
| 多租户、SSO、细粒度权限 | 本期定位单团队私有部署（10.11） |
| 界面承载业务判断（如自动决定章节归属） | 判断属内核与 Agent，界面只呈现结果与收集裁决 |
| 外发通知与审批流 | 数据边界优先；审批流属 P3 |
| 界面自行推断作业聚合状态 | 聚合规则唯一来源是服务端；前端推断会在枚举演进时产生歧义 |

### 7.9 开放问题

留给下一轮设计裁决，均已有倾向但需要确认：

1. **模板入库是否需要"重新解析"的差异预览？** 当模板原件修正后重新入库，契约可能变化。倾向：重新入库走同一向导，第 3 步直接展示与上一版本的契约差异（不做单独功能）。
2. **裁决待办是全局还是项目内？** 当前设计为全局 Inbox + 按项目分组。风险是条目量大时噪音高，可加"仅看当前项目"的默认筛选。
3. **是否需要"预览构建"（只渲染前若干页）？** 详细设计类文档构建是分钟级，全量等待对迭代不友好。倾向 P1 增加"快速预览"作业类型，仅渲染指定章节或指定子作业。
4. **事实源的字段级映射是否需要界面？** 当前用配置文件（模板化默认映射）。若外部用户接入成本过高，可能需要在 P06 增加一个**只读**的映射预览，而非可编辑映射器。
5. **子作业并发上限如何暴露？** 子作业可并行（见 4.8），但并发上限受 worker 数与模型服务吞吐约束。倾向：在 P08 发起面板只读显示当前可用并发，不做用户可调参数（避免自部署场景下被误设）。

> 原"多文档族的作业粒度"一项已裁决：**一个编排作业 + 多个子作业**（见 4.7、7.6.1）。

### 7.10 落地顺序建议

界面工作量最容易失控，因此按"能否支撑一次完整交付"排序，而不是按页面顺眼程度排序：

| 批次 | 页面 | 判据 |
| --- | --- | --- |
| **第一批（最小闭环）** | P01 项目列表（含演示项目）、P05 入库向导、P09 作业详情、P10 门禁裁决 | 缺任何一页，都无法在浏览器内完成"入库 → 构建 → 看结果 → 裁决"这条完整链路 |
| **第二批（可用）** | P02 项目总览、P06 事实源、P07 文档配置、P08 作业列表与发起、P11 产物与对比 | 补上配置与产物管理，使系统可被日常使用 |
| **第三批（可信）** | P04 模板包详情、P12 裁决待办、P13 设置 | 提升核对能力与可追溯性；**P13 与数据边界、模型端点相关，实为 P0 级别的必要页**，建议随第一批一并实现 |
| **第四批（增值）** | P03 模板库完整能力、P14 漂移监控 | 支持模板资产化与长期维护 |

**一条纪律**：第一批不以"页面好看"为验收标准，而以"完整闭环可在浏览器内跑通且无命令行介入"为验收标准（对应验收 27、35）。

## 8. 创新与拓展功能

本章为超出「复刻模板」本身的增值能力，按落地难度与价值排序。每项标注**前置能力**（依赖本设计中哪些能力先可用），避免空想。

**开源归属建议**（决定这些能力应该放在哪里实现，避免核心仓库被行业特化内容污染）：

| 归属 | 能力 | 理由 |
| --- | --- | --- |
| **主仓库（引擎核心）** | 8.1 档案与皮肤包复用、8.2 血缘图谱、8.3 漂移雷达、8.6 Prompt-to-Section、8.8 影响面预演、8.9 多文档族联动、8.10 图片资产化 | 与具体行业标准无关，是通用工程能力，应成为所有人开箱可用的能力 |
| **官方独立包** | 8.4 体例合规校验器、8.5 AI 评审员 | 依赖特定体例与行业标准（如行业文档规范），放入核心会让仓库被特化规则污染、且每接一个行业就要改核心 |
| **社区扩展** | 特定行业模板包、领域专用规则集、专有事实源 Connector | 由使用方自持；主仓库只维护索引与规范符合性声明（见 2.4） |

### 8.1 文档类型档案与皮肤包（跨项目、跨类型复用）

**说明**：模板库与文档类型档案已由 6.2 提升为 P0 核心能力，本条是其延伸能力。

**问题**：模板库沉淀的是「版式」，档案沉淀的是「体例」。两者若都只能在本项目内使用，换团队时仍要从零解析模板、重写体例、重踩一遍差异。

**方案**：把两者分别抽象为可移植资产——
- **文档皮肤包**：剥离文件编号与业务术语的模板包（样式契约 + 结构骨架 + 版块库 + 指纹），换项目只做差异适配（术语表、编号规则、章节映射）；
- **文档类型档案包**：`doc_type_profile` + 体例 + 投影规则 + 规则集 + 样例输入，**自带适用判据说明**，可在不同组织间交换。

**这是本项目最可能形成社区积累的东西**：模板包与档案的多样性无法由单一团队产出，而它们恰好是纯数据资产、贡献门槛最低（见 2.4、3.1、10.8）。

**前置能力**：依赖 6.2 的模板包格式与档案格式先稳定——本条不引入新机制，只增加一层可移植性约束。

**价值**：新项目接入从"数天"降到"数小时"；同一套体例下的多个产品线共享一份皮肤；跨行业复用同一份引擎与档案格式。

### 8.2 文档血缘图谱与追溯矩阵

**问题**：评审时被问"这个接口在文档哪一节""这条需求落到哪几张表"，只能人工翻。

**方案**：构建需求 → 接口 → 数据表 → 文档章节 → 表格/图 的有向图，支持：
- **正向查询**：给定一条需求，列出全部落位点；
- **反向查询**：给定文档一节，列出它依据的需求与接口；
- **缺口分析**：哪些接口没有章节、哪些章节没有事实源支撑。

**价值**：评审从"翻文档"变成"查图谱"；覆盖率缺口自动暴露。

### 8.3 文档漂移雷达

**问题**：代码先改、文档后补，或干脆忘补，交付时才发现不一致。

**方案**：构建时固化事实快照；后续定时（或 CI 钩子触发）重新提取事实并与快照比对，输出漂移清单：
- **已变更未同步**：接口新增/删除/字段变化，文档未更新；
- **已同步未验证**：文档改了但事实源未变，疑似笔误；
- **长期未动**：章节超过 N 个版本未更新，提示复核。

**价值**：把"文档过期"从交付风险变成日常提示。

### 8.4 体例合规校验器（标准规则集）

**问题**：体例要求散落在口头约定与评审意见里，新人无法自助。

**方案**：把体例写成可配置规则集，例如：
- 标题层级与命名规则、编号连续性与不重复；
- 表格必须用于比较/字段/参数/状态/权限/验收等场景，禁止长段落替代；
- 表格列头固定用法（名称/数据类型/是否允许为空/描述），数据类型取值域受限；
- 表格内描述不带句末句号，正文描述带句号；
- 图题格式与编号连续；
- 术语白名单/黑名单。

规则集可绑定到文档类型，构建时逐条校验并给出定位。

**价值**：体例从"人的记忆"变成"机器的规则"。

### 8.5 AI 评审员

**问题**：文档评审靠人读，深章节（60+ 页）容易漏看。

**方案**：以模板契约与体例规则为 rubric，对文档做结构化评审，输出三类结论：
1. **缺失**：该有的章节/表格/字段没写；
2. **薄弱**：只有结论没有依据、只有名词没有行为、异常与边界分支缺失；
3. **矛盾**：前后术语不一致、与事实源冲突、与产品需求冲突。

评审结果按严重级别排序，附原文定位与修订建议。

**价值**：把评审从"通读"变成"复核机器的结论"，人只做裁决。

### 8.6 自然语言生成章节（Prompt-to-Section）

**问题**：小范围补写章节时，仍要人工对齐模板体例。

**方案**：输入一句意图（"补一节说明质控数据的采集与校验流程"），系统：
1. 从结构骨架定位插入位置；
2. 从事实源检索相关内容（接口、表、状态机）；
3. 生成符合模板体例的章节草稿（含表格与图槽位）；
4. 通过门禁校验后给出 diff 供确认。

**约束**：生成内容不得引入事实源之外的断言；无法确认的标注"待确认"。

### 8.7 模板逆向工程

**问题**：手里只有一份历史交付文档，没有模板，但新文档要沿用它的格式。

**方案**：从既有文档反推模板契约（样式层、结构骨架、版块库、体例特征），生成"文档皮肤包"，供后续文档复用。

**前置能力**：复用 6.2 的入库解析器；差异只在于输入是成品文档而非模板，需额外区分「内容已填充」与「样式层可提取」的边界。

**价值**：把存量交付物变成可复用资产。

### 8.8 变更影响面预演（What-if Preview）

**问题**：改一个接口前，不知道会牵动多少文档工作。

**方案**：输入拟变更项，系统基于血缘图谱与体例规则，预演受影响范围：涉及的章节、需要重绘的图、需要重跑的表格、可能触发门禁失败的规则，并给出工作量估算（受影响章节数 / 表格数 / 图数）。

**价值**：把文档成本前置到技术方案阶段，避免"改完才发现文档要重做"。

### 8.9 多文档族联动

**问题**：一套交付物含概要、详细、数据库三份，甚至再加测试方案，相互引用与编号容易不自洽。

**方案**：以同一份事实源与同一套术语/编号规则驱动整个文档族：
- 交叉引用自洽（详细设计提到的模块在概要有定义）；
- 编号体系统一（图、表、章节编号按文档族规则生成）；
- 术语与命名全族一致；
- 任一文档更新后，自动标记其余文档的关联章节待复核。

### 8.10 图片与图表资产化

**问题**：图靠截图与手绘，风格不统一、编号易断、改一处要重排多图。

**方案**：图表程序化生成（架构/流程/数据流/ER/部署），风格参数化；图题与图号由系统管理；图源与文档分离，改图源即可重出全部文档，图号自动重编。

**前置能力**：依赖 6.3 FR-M3-07 的图表程序化生成能力先可用；本条是其参数化与资产化升级，不引入新的渲染技术。

## 9. 非功能需求

| 编号 | 类别 | 需求 |
| --- | --- | --- |
| NFR-01 | 保真度 | 样式定义与已入库契约的归一化结构一致；受保护文本不变，内容槽位按 IR 替换；编号、分页、几何及域刷新变化须由配置和允许属性白名单约束，不承诺整个文件字节不变 |

| NFR-10 | 可扩展 | 新增文档类型、新增事实源 Connector、新增门禁规则均为插件式接入，不改动核心链路 |
| NFR-11 | 中文优先 | 代码注释、文档内容以中文为主；标识符与协议字段保留英文 |
| NFR-12 | 可移植 | 核心逻辑不绑定 Windows；仅 Word COM 能力标注平台限制 |
| NFR-13 | 模型无关 | 不绑定具体模型与供应商；**LLM 可完全关闭**，关闭后核心链路仍能产出文档（文案退化为模板化描述） |
| NFR-14 | Agent 可替换 | Agent 定义与业务逻辑解耦，单个 Agent 可被替换或降级为纯代码流程，不影响其余链路 |
| NFR-15 | 决策可解释 | Agent 的每条判定（跳过 / 判重 / 豁免）必须输出理由并归档到构建报告 |
| NFR-16 | 断点可恢复 | 长流程支持从运行状态快照恢复，不重跑已完成阶段 |
| NFR-17 | 提示词版本化 | Agent 的 instructions 与工具描述纳入版本管理，变更必须附回归结果 |
| NFR-18 | 成本可控 | token 用量按 Agent 与阶段归集；提供纯确定性模式作为零成本退路 |
| NFR-19 | 长任务健壮 | 作业状态持久化，服务重启后未完成作业可识别并续跑；构建过程不残留不可恢复的中间态 |
| NFR-20 | 内核纯净 | 引擎内核零 Web 依赖，可在无 HTTP、无数据库环境下独立运行与测试（见 2.5） |
| NFR-21 | 数据边界 | 默认不向外发送上传内容；LLM 默认关闭；启用后仅向显式授权端点发送声明范围内的必要、脱敏内容；密钥不写入前端、日志与作业记录（见 10.11） |
| NFR-22 | 前端轻量 | 界面不承载业务规则与判断逻辑；呈现优先，交互复杂度受控，避免前端投入挤占内核 |

| NFR-23 | 模型实测准入 | 使用显式配置模型逐点评测；模型接管点达到声明的基线通过率，其余由规则或人工接管；不限定参数量、量化或部署位置；**未达阈值的决策点不得交给模型**（见 5.2.3） |
| NFR-24 | 结构化输出强制 | 采用的 Agent 输出 100% 经 Schema 校验；按端点能力启用 JSON Schema / 受限解码，不支持时由字段约束、校验、有限重试与规则兜底保证链路不中断 |
| NFR-25 | 决策面收敛 | 单 Agent 工具数 ≤ 7、参数扁平；单次决策的上下文有明确上限，按决策点检索裁剪，不投喂全量契约与事实 |
| NFR-26 | 降级不阻断 | 模型不可用、输出校验失败、置信度缺失或低于阈值时，默认走规则值并把该项标记「待确认」送入裁决队列；**构建不得因此失败**；替代准入策略须满足 5.2.4 |
| NFR-27 | 配置模型接入 | 经 OpenAI 兼容端点接入显式配置且授权的模型服务；与构建 worker 分离部署；模型关闭时本应用零模型请求、不启动推理进程；禁止隐式云端回退与 tracing 外发 |
| NFR-28 | 类型无关 | 引擎代码中不出现任何文档类型名称与领域概念名称（可自动检索校验）；新增文档类型不需要修改引擎代码（见 4.9、验收 42） |
| NFR-29 | 同源多型 | 同一事实包可产出 ≥ 2 种结构形态不同的文档类型，事实逐项一致、样式各自保真（通用性的可验收形式，见 4.9.5） |

## 10. 开源项目设计

### 10.1 开源边界（合规红线）

| 可以开源 | 禁止入库 |
| --- | --- |
| 引擎代码（解析 / 契约 / 编排 / 渲染 / 门禁 / Agent 定义） | **模板 docx**（甲方提供，版权归属需确认） |
| 自制示例模板与**自制示例档案**（无业务信息、可公开；**通用性验证靠的就是它们**） | 生成的交付文档（项目机密 / 注册资料） |
| 规则与体例**格式规范**、剥离业务术语的示例体例配置 | 项目实际使用的**文档类型档案**（含真实章节与术语）；截图、设计图、PRD 原件 |
| 文档、示例与测试 | 任何真实项目的事实源（OpenAPI 导出、ORM、proto、变更点 xlsx） |

**必须提请注意 —— 这是本项目开源的最大前置风险**。本项目源于公司交付物的生产实践，开源前必须确认：

1. 代码归属是否允许对外开源（职务作品 / 公司资产归属）；
2. 模板与体例是否涉及甲方合同保密条款（**模板是甲方的，不是我们的**）；
3. 是否需要走公司开源审批流程。

**未取得明确授权前，只应以私有仓库形式存在。** 开源范围建议限定为"抽象后的通用引擎 + 自制示例"，不得包含任何真实项目素材。

**反向约束同样重要：剥离的只能是数据，不能是能力。** 若某项能力目前只存在于私有模板上（例如跨模板版块组合、修订记录表的固定单元格版式、超长图等比缩放），必须用自制示例模板复现出同等配置。否则开源版会退化成"看起来很酷但干不了活"的演示品——这是同类项目最常见的失败形态。具体要求见 10.10。

### 10.4 对外价值主张（README 首屏口径）

同类项目对比见 2.3，本节只定义**对外宣称的口径**——开源项目的第一屏决定了绝大多数访问者是否继续往下看。

| 问题 | 统一口径 |
| --- | --- |
| 这是什么 | 模板与体例驱动的**通用**文档撰写引擎：**不改模板样式，只注入内容**；**与文档类型无关** |
| 解决什么 | 有模板约束、结构可枚举、内容可溯源的**各类文档**（设计 / 需求 / 测试 / 手册 / 报告 / 作业程序 / 招投标……）反复人工排版与合规检查 |
| 凭什么 | 样式层零改动 + 版块原型复用 + 门禁拦截 + **换文档类型只写配置**；能力来自真实交付踩坑，不是提示词 |

首屏必须给到的三样东西：

1. 一张**保真度对照** —— 产出文档与模板的样式一致性证据（真实产物对照，不是示意图）；
2. 一条**一行可复制**的启动命令（`docker compose up`），浏览器打开即可用示例数据跑通（离线、无需 API Key）；
3. 一张**能力边界表**（做什么 / 不做什么），提前消除预期错位；
4. 一组**同源多型示例** —— 同一份事实源产出至少三类文档，直接证明"与文档类型无关"不是宣称（见 4.9.5、10.10）。

**禁止的宣称**：不得出现"一键生成完整文档""无需人工""替代文档工程师"这类表述。原因很实际——预期错位会同时招致两类反噬：普通使用者试完后给差评，而真正需要它的评审场景反而不信任它。

**唯一难以被替代的能力是"样式零偏差"** —— 它来自真实交付中的反复踩坑（见 1.2 的 12 条痛点），不是提示词能堆出来的。这条应放在最显眼处，因为它是使用者唯一真正在意的东西。

### 10.5 命名与查重（已执行，结论：`docforge` 不可用）

设计阶段即完成命名查重——仓库名与 PyPI 包名一旦发布极难更改（PyPI 包名删除后不可复用）。实测结果：

| 已占用名称 | 类型 / 定位 | 冲突程度 |
| --- | --- | --- |
| `vukan322/docforge` | Go 库，MIT，DOCX 模板渲染，明确宣称"不修改文档样式" | **最严重：同名 + 理念高度重叠** |
| `gardener/docforge` | Go，Apache-2.0，Documentation-as-Code 工具 | 同名，赛道不同 |
| `Shriyabh11/DocForge` | Python，代码文档自动生成（CodeT5 微调） | 同名，赛道不同 |
| `QQSHI13/docsforge` | Python，MkDocs-Material 替代方案 | 近似名 |
| PyPI `docforge` | Python 包名 | 已被占用 |

**结论：`docforge` 三重叠加（GitHub 同名 + PyPI 占名 + 理念重叠），不可用。**

命名原则：

1. **唯一可检索** —— 首次命名时核验 GitHub、PyPI 与域名占用；后续发布核验所需权限，不要求已拥有的仓库再次查空；
2. **语义直指差异化** —— 指向"模板保真"而非泛化的"文档生成"；
3. **避开高频组合** —— `doc/docx + forge/generate/maker` 这类组合撞名概率极高，应主动规避；
4. **撞名即退让** —— 不赌"赛道不同"，历史上同名项目合并与混淆的成本远高于改名。

**已定稿：`docfidelity`**（2026-09-21；PyPI `docfidelity` / GitHub 用户名 / `docfidelity.com`·`.cn`·`.org` 三处实测均未被占用）。下列候选方向不再采用。

> 对应条目 `OS-18` 由 P1 **提级为 P0**，且范围由"查重"升级为"命名定稿"——已于 2026-09-21 锁定为 `docfidelity`（该名自始即用于工程代号，故无仓库结构 / 包名 / 导入路径返工）。

### 10.6 兼容性承诺与弃用政策

开源项目的信任来自"升级不会突然弄坏我的东西"。本节把承诺分级写死：

| 对象 | 稳定度 | 破坏性变更要求 |
| --- | --- | --- |
| HTTP API 路径与请求 / 响应结构 | Stable | 升主版本 + 迁移指引 |
| 作业状态与阶段枚举值 | Stable | 允许新增取值；改名或删除须走弃用流程 |
| Web 界面路由与关键操作路径 | Beta | 可调整，但不得在未告知的情况下让既有操作路径失效 |
| 模板包格式（含自带 `format_version`） | Stable | 升主版本；旧包须能被识别并给出明确升级提示 |
| 内容 IR 格式 | Stable | 升主版本 + 提供转换脚本 |
| 门禁规则格式 | Stable | 升主版本 + 规则迁移说明 |
| 扩展点接口 | 见 4.5 分级 | 按对应级别执行 |
| Python 公开 API | Stable | 升主版本 |
| 内部实现（`_` 前缀） | 不承诺 | 无 |
| Agent 提示词与工具描述 | Experimental | 无承诺，但需在 CHANGELOG 说明 |

**弃用流程（禁止静默移除）**：标记弃用 → 文档标注 + 运行时告警（至少持续一个小版本）→ 下一主版本移除。

### 10.9 测试策略与可复现性

开源 CI 有一条硬约束：**不能依赖真实 LLM API**。原因有三——成本、非确定性（flaky）、密钥泄露风险。

| 层级 | 内容 | 需 API |
| --- | --- | --- |
| 单元 | 契约模型、OOXML 操作、几何计算、规则判定 | 否 |
| 集成 | 示例模板入库 → 构建 → 门禁全链路；golden 文件比对 | 否 |
| 服务端 | API 契约测试 + 作业状态机（重启续跑、取消、并发提交） | 否 |
| 端到端 | 浏览器完成"上传 → 构建 → 审阅 → 下载"主流程 | 否 |
| Agent | 录制响应回放（record / replay）或 stub 模型，跑通决策路径与护栏 | 否 |
| 冒烟 | 真实模型连通性验证 | 是，仅手动触发，不进 PR 门禁 |

配套要求：

1. **确定性模式是一等公民** —— 确定性模式下全链路不调用模型，CI 默认启用（呼应 NFR-13 / OS-14）。
2. **golden 文件比对"结构快照"而非文件字节** —— 比对段落数、样式引用、表格行列、图片 `wp:extent`、分页位置。OOXML 字节受时间戳与部件 ID 影响，直接比对字节必然 flaky（1.2 第 7 条问题即此类教训）。
3. **最小复现输入** —— 报告者需提供**作业配置导出文件** + 自制样例（工作台提供"导出复现包"功能），使维护者能在无私有数据的环境中复现。这条同时也是 10.1 合规红线的落地手段。
4. **内核测试不得启动 Web 服务** —— 引擎的单元与集成测试在无 HTTP、无数据库的环境下必须能跑通。这既是 2.5 边界的验证方式，也是防止"渲染与 HTTP 耦合"回流的门禁。

### 10.10 示例资产的完备性要求（开源版可用性的前提）

这是本项目最容易做错、也最容易被忽视的一点：**真实能力都由甲方模板驱动，开源版若只带一个"Hello World 模板"，外部用户会判定项目无用。**

**而且必须跨文档类型。** 示例若只覆盖一类文档，等于向外部宣告"这工具只做那一种"，通用性也就无从验证。因此示例资产必须能**一一对应地展示全部能力，并跨至少三类文档类型**：

| 示例模板须覆盖 | 对应能力 |
| --- | --- |
| 多级标题 + 自动编号 | 结构骨架、编号契约 |
| 封面 + 修订记录 + 页眉页脚 | 版块库与跨版块引用 |
| 多种表格原型（含合并单元格、跨行跨列） | 表格规范化与列宽契约 |
| 目录域 + 页码 + 分节 | 域刷新与分页策略 |
| 长图与宽图槽位 | 版心内等比缩放 |
| 带编写说明的占位内容 | 占位清理规则 |
| 冗余模块（如"参考资料"） | 模板裁剪能力 |
| 跨模板组合（封面取 A、修订表取 B） | 版块按 `block_id` 引用 |

| 示例需覆盖的**文档类型**（≥ 3 类，结构形态须不同） | 对应能力 |
| --- | --- |
| 一接口一节型（逐条展开，含参数表 / 响应表） | 投影规则 `layout: one_section_per` |
| 一模块一表型（汇总表为主，粒度不同） | 同一事实包换 `layout` 与字段映射 |
| 非软件域文档（如标准作业程序 / 评估报告，含步骤、阈值、签核栏） | 领域模型可扩展、体例可声明、渲染策略可复用 |

**并且必须做到"一键可体验"**：`docker compose up` 后浏览器打开即可用内置示例数据跑通全流程，**并可切换至少三类示例文档，当场看到「同一份事实源 → 三种文档产出」**——这是通用性最直观的证明。开源项目的试用路径每多一步，愿意认真评估的人就少一批。

并需附一份**对照说明**：同一份事实源下，本系统产出 vs 手工排版的差异点清单，让使用者在 5 分钟内判断保真度是否达到要求。

### 10.11 Web 端与数据边界（引入 Web 后的新增红线）

Web 端引入了一类此前完全不存在的风险：**服务端会接收甲方模板与项目事实源文件**——而这些恰好是 10.1 明令禁止入库的资产。因此必须把数据边界作为设计约束，而不是部署时的运维细节。

| 项 | 约定 |
| --- | --- |
| 数据流向 | 默认**本地 / 内网私有部署**，不向外发送上传文件、模板或事实源内容；启用模型后，仅可向使用方显式配置且授权的端点发送声明范围内的必要、脱敏内容，不得默认上传完整文件 |
| LLM 调用边界 | **默认关闭**；支持本地、内网或显式授权的外部 OpenAI 兼容端点；明确告知"哪些内容会离开本机"并提供**内容脱敏 / 完全关闭**选项；禁止 SDK tracing 外发与默认云端回退；用运行期网络记录核对无未授权出口 |
| 密钥管理 | 模型 API Key 仅存于服务端配置或环境变量，不下发前端、不写入日志与作业记录 |
| 作业产物保留 | 保留策略可配置，提供一键清理，避免服务端成为甲方文档的长期存放地 |
| 上传校验 | 上传即校验类型、大小与可解析性；拒绝可执行文件及压缩包内的可执行内容（zip 炸弹、路径穿越） |
| 演示模式 | 内置示例数据的演示模式，可在**不引入任何真实模板**的前提下体验全流程（与 10.10 呼应） |
| 多租户 | 本期为单团队自部署，**不做 SaaS 多租户**；若将来暴露公网，须先补齐鉴权、隔离与审计 |

**边界原则：部署位置与显式授权的模型端点共同决定数据流向。** 首页与部署文档须明确默认关闭模型，以及启用后哪些必要内容会离开本机；私有部署本身不能证明零外部请求。

## 11. 验收标准

验收**只依赖系统自身的产出**：用自制示例模板 + 内置样例事实源，按**至少三份文档类型档案**（两类软件文档 + 一类非软件域文档）产出，逐项判定；其中验收 42–45 专门判定通用性。任何既有项目的模板、文档与产物都不参与判定（见附录 B）；如需外部对照，只能作为参考附注，不能作为通过条件。

需全部满足：

| 序号 | 验收项 | 判定标准 |
| --- | --- | --- |
| 1 | 文档产出 | 按某份文档类型档案一键产出一套 docx（示例为设计文档族三份，可由档案替换为其他文档类型），命名符合档案声明的命名规则 |
| 2 | 样式保真 | 与已入库模板包契约比较归一化样式结构：定义一致、引用的 styleId 全部存在、无未许可直设格式残留；不在生成期重新解析或对比模板 |
| 3 | 版式合规 | 表头加粗缺失 0、数据行误加粗 0、底纹残留 0、表格越界 0 |
| 4 | 分页合规 | 正文分页符 0，仅封面、修订记录、目录三处允许分页 |
| 5 | 图片合规 | 全部图片落在版心内，无裁剪、无越界，图注与图不分离 |
| 6 | 术语一致 | 软件名与模块名全局一致，禁用旧称命中 0，替换后无连读重复 |
| 7 | 内容完整 | 模板槽位未填 0、占位提示残留 0、参考资料类模块残留 0 |
| 8 | 事实一致 | 文档中的接口数量、字段清单、表结构与事实源逐项一致；无法被事实源验证的内容已标注「目标设计」或「待确认」 |
| 9 | 稳定比对 | 归一化易变标识后，两次构建文本差异行数 = 0 |
| 10 | 可复现 | 冻结相同输入、配置与运行姿态，归一化文本与结构快照稳定；实际页数另在固定排版引擎版本、字体和 locale 的环境验证，无排版环境时明确标为未验证 |

| 12 | 追溯可查 | 任取一个接口，可在报告中查到其所在章节；任取一节，可查到其事实来源 |
| 13 | 模板库生效 | 模板入库后，生成期不再执行模板解析与样式对比（仅深拷贝读取原件）；同一模板连续生成 3 次，产物一致 |
| 14 | 模板版本可比 | 同一 `template_id` 的两个版本入库后，能输出样式层 / 结构 / 表原型 / 页面设置的差异清单与影响面 |
| 15 | 契约自足 | 生成期所需的全部版式决策（标题样式、允许块类型、列宽、版心、槽位、编号）均可直接从模板包契约查到，无需回读原件现算 |
| 16 | 包完整性 | 每个模板包通过完整性校验：文件齐全、JSON 可解析、原件可正常深拷贝、契约与原件实际状态一致 |

| 18 | LLM 可关闭 | 关闭 LLM 后，示例文档族仍可产出并通过全部门禁（文案退化为模板化描述） |
| 19 | 决策可审计 | 构建报告含每个 Agent 的判定清单与理由，可按 `run_id` 追溯至 trace |
| 20 | 开源可跑通 | 外部开发者 clone 仓库后，用自制示例模板可在无私有数据的情况下跑通全流程 |
| 21 | 新人上手成本 | 从 clone 到产出第一份文档 ≤ 30 分钟，全程**不需要 API Key**、不需要真实模板、不需要 Office |
| 22 | 命名无冲突 | 项目名、PyPI 包名与导入路径一致；首次发布前验证所需发布权限与外部命名占用，已拥有的项目仓库不要求查空 |

## 12. 迭代规划

| 阶段 | 目标 | 主要内容 | 退出条件 |
| --- | --- | --- | --- |
| **P0 内核 + Web 骨架** | 确定性内核可复用、**能在浏览器里跑通**，且开源条件同时成立 | 确定性能力全部封装为 function tool；M1 统一 Connector；**M2 模板入库（解析前置）+ 模板包**；M3 内容 IR 抽象 + **文档类型档案与投影规则（4.9）**；**领域模型框架（开放 `kind`）**；M4 渲染策略化；M5 门禁规则化；**M7 Web 工作台主流程（上传 / 作业 / 进度 / 报告 / 下载）+ 作业状态持久化 + 编排作业派生多个子作业（含失败隔离与局部重跑）**；5 个 Agent 骨架 + 纯确定性模式 + **决策点分级与配置模型逐点基线（结构化输出 + 规则兜底 + 置信度缺失 / 低置信降级）**；**依赖规则门禁（4.6）**；**命名定稿 · LICENSE · README · CONTRIBUTING · GOVERNANCE · ROADMAP · CI · Docker 自部署 · 示例模板（覆盖 10.10）** | 浏览器内用示例数据跑通全流程且 CI 绿；用示例模板产出**三类文档类型**（含一类非软件域）并通过第 11 章全部验收项（含验收 42–45）；示例模板已入库、生成期不再解析模板；**关闭 LLM 仍能产出合规文档**；**模型不可用或未达基线时链路仍成立，未准入项进入裁决队列而非静默采用**；**内核可在无 Web 环境下独立测试**；**依赖规则检查通过（无越界导入）** |
| **P1 通用化与首次发布** | 换项目、换模板、**换文档类型**均可用，具备对外发布条件 | 模板包与**文档类型档案**跨项目复用；体例配置外置；**档案打包导出 / 导入**；追溯矩阵；多项目隔离；回归基线；**模型决策点扩展与能力路由灰度（逐点提升模型接管比例）**；**首次发布：Docker 镜像 + 部署文档**（PyPI 包与库级 SDK 后置） | 外部使用者用第二套模板与**第二类文档类型档案**（结构形态与示例不同）在浏览器内**零代码**跑通全流程；验收 21–45 通过 |
| **P2 智能化** | 五个 Agent 全量接管 | Curator / Architect / Composer / Renderer / Inspector 全链路 + guardrails + tracing；变更点增量更新 + 批注；漂移雷达；AI 评审员；Prompt-to-Section | 一次真实变更点迭代全程由 Agent 编排完成，人工只做审批与裁决 |
| **P3 生态与 1.0** | 社区与生态成立 | 模板包与**文档类型档案**的索引及社区贡献流程运转；模板库管理界面完善；**CLI 与 CI 门禁（后置项解禁）**；变更留痕与审批流；影响面预演；**对外格式冻结并进入严格 SemVer** | 至少 1 个外部贡献的模板包、文档类型档案或扩展被合入；v1.0 满足 10.6 的全部兼容承诺 |

**为什么 Web 端进 P0，而不是当作最后一层皮。** Web 化会反向约束内核接口——"引擎必须能在没有 HTTP 上下文的情况下被调用"这条约束，只有第一天就要求才可能自然成立。若先做内核、最后补 Web 界面，几乎必然要把参数、状态与错误处理全部重构一遍，等于把"内容与版式耦合"的教训再交一次学费。

**为什么把开源骨架放进 P0。** 见过太多项目把"开源化"安排在收尾阶段，结果卡在私有依赖、私有路径、私有模板上无法脱身——**这类耦合一旦形成，剥离成本远高于一开始就不引入**。本项目把命名定稿、许可证、社区文件、示例模板、CI、确定性模式全部列为 P0 交付内容，理由只有一条：开源属性必须从第一行代码开始成立，而不是靠最后一次重构补上。

**为什么把模型逐点基线放进 P0。** 模型能力会影响决策点、候选集、工具描述与降级路径，不能只凭模型名称或 HTTP 成功宣称可靠。主流程集成与身份匹配的真实基线应一并验证；不限定模型规模，也不以全部退回规则冒充模型集成完成。剩余工作的日期、依赖与退出条件见 [路线图](../../ROADMAP.md)。

**为什么通用性必须在 P0 就被约束，而不是等有了第二个文档类型再重构。** 因为"类型无关"是**反向约束**：它决定领域模型怎么切、内容单元怎么定义、投影规则怎么表达。若先按一类文档把链路写通，第二个文档类型到来时要做的是**把领域概念与文档类型从引擎里剥出来**——那比"内容与版式解耦"更彻底，4.9.1 的三条解耦要全部重做。因此 P0 的退出条件里含"第三类文档类型零代码接入"。

同时保留一条纪律：P0 的验收以**等价能力**为准（系统能独立产出与既有交付物同等质量、且覆盖多种文档类型的文档），不以功能数量为准。**范围蔓延是本项目最大的内部风险**（见第 13 章）。

## 13. 风险与约束

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 模板样式差异需人工裁决 | 跨模板对齐时，样式"语义相同但命名不同"无法自动判定 | 建立样式别名映射表，无法判定时输出差异清单交人工确认，不做猜测 |
| Word COM 依赖 | 域刷新、PDF 导出依赖本机 Word，存在锁文件、静默不覆盖等行为 | 明确降级路径与提示；锁文件与转换产物时间戳纳入检查 |
| LLM 生成的事实风险 | 生成的描述可能超出事实源 | LLM 输出必须经体例与事实双重校验，无法验证的内容强制标注"待确认" |
| 模板冗余裁剪误删 | 按关键词定位可能误伤正文 | 裁剪规则要求定位到"标题 + 段落 + 表格"完整块，且裁剪前后做文本快照比对 |
| 编号/样式压缩引发回归 | 合并 numbering 定义可能改变既有编号外观 | 编号操作后必须做视觉抽页比对与编号连续性校验 |
| 图片越界不可见 | Word 对超长图是裁剪而非跨页，页数检查无效 | 强制量 `wp:extent`，禁用"按页数判断是否越界" |
| 体例知识集中在个人 | 体例要求目前依赖个人经验 | 用 P0/P1 阶段把体例写进配置文件与规则集，形成可传承资产 |
| 范围蔓延 | 系统本身可能变成新的大工程 | 严格按 P0 退出条件收敛；先让内核与边界成立，再谈创新项 |
| 开源合规 | 代码归属与模板版权未确认；甲方合同可能含保密条款，**模板属甲方资产** | **未取得公司明确授权前只建私有仓库**；开源范围限定为抽象引擎 + 自制示例；见 10.1 |
| 命名冲突 | `docforge` 已被多个项目占用，其中 `vukan322/docforge` 是同领域的 DOCX 模板渲染库 | P0 内完成命名定稿，改用唯一且语义明确的名称；见 10.5 |
| 巴士因子 | 单人维护的项目停更即死亡；发布权限与全链路知识集中在创建者身上 | 早期引入第二维护者；关键决策留档（ADR）；避免只有作者能懂的隐式约定；见 10.7 |
| 上游依赖演进 | `openai-agents` 等上游包处于 0.x 阶段，破坏性变更频繁 | 上游用法收敛到**薄适配层**并锁定版本区间；核心链路不直接依赖上游对象模型 |
| 冷启动无使用者 | 发布后无人使用，反馈闭环与贡献者都建立不起来 | 首版即提供可对照的保真度 demo；优先在同样受模板约束的团队中试点，用真实模板验证；见 10.10 |
| 社区期望偏离主线 | 开源后功能请求会偏离"模板保真"主线 | 以"是否破坏模板保真 / 可复现"为唯一裁决判据；用公开 Roadmap 管理预期；见 10.7 |
| 外部无法验证 | 外部用户不愿为验证功能承担模型 API 费用 | 确定性模式为零成本默认路径；模型环节可关闭、可录制回放；见 10.9 |
| Web 长任务中断 | 构建为分钟级，同步请求必然超时；服务重启会丢失进行中的作业 | 作业化 + 状态持久化 + 阶段续跑；**禁止同步等待式构建接口**；见 3.2 场景 G |
| Web 端成为耦合入口 | 渲染逻辑被写进 API 层或前端，导致引擎无法独立测试与扩展 | 分层约束：内核零 Web 依赖；`tests/unit` 必须在无 HTTP 环境下通过（验收 32） |
| 上传文件安全 | 服务端接收用户上传的 docx 与压缩包，存在路径穿越、zip 炸弹、宏文档风险 | 上传即校验、不执行上传内容、解析限定在受限目录内、拒绝可执行内容；见 10.11 |
| 数据外流 | 模板与事实源属甲方资产，Web 化后存在被发往未授权服务的风险 | 默认私有部署 + LLM 默认关闭 + 显式授权端点与必要内容脱敏 + 密钥不入前端与日志；运行期核验出口；见 10.11 |
| 前端投入挤占内核 | 界面工作量容易失控，P0 被 UI 细节拖住 | 界面只做表格 / 表单 / 报告与目检图呈现，不做可视化编排；先跑通主流程，再谈体验 |
| LLM 不可复现 | 相同输入可能产出不同文案，破坏"确定性构建"承诺 | 确定性链路与 LLM 环节严格隔离；LLM 输出缓存并纳入产物哈希；提供纯确定性模式 |
| Agent 越界 | 模型自行尝试直接改 OOXML，导致样式损坏且不可复现 | 工具层不暴露任何 OOXML 直写能力；输出护栏在写盘前校验契约；见 5.3 |

| 模型能力不足 | 任何模型均可能工具误选、结构化输出失败、判定跳步或缺失置信度；端点成功不代表任务正确 | 决策面收窄 + 结构化输出校验 + 候选注入 + 规则兜底；逐点真实基线与准入依据必须匹配，**未达阈值的点不交给模型**；见 5.2 |
| 提示词随模型漂移 | 换模型或换版本后 instructions 与工具描述失效，行为静默变化 | 薄适配层隔离 + 提示词版本化 + 录制回放回归（见 10.9）；基线通过率纳入 CI |
| 模型服务资源与可用性 | 自部署服务可能争抢算力，外部服务可能限流、超时或中断，影响构建吞吐 | 模型服务与 worker 解耦、有限重试与规则降级；关闭后本应用零模型请求，不启动推理进程；见 4.8 |
| 决策点归属蔓延 | 实现期「顺手让模型判断一下」，把本该是规则的事交给模型，稳定性持续下降 | 决策点分级表（5.2.3）作为评审项；新增决策点必须先归类并登记路由配置 |
| 通用性滑向万能工具 | "支持任何文档"若不加判据，设计会被无数特例拉扯，每条链路都做不深 | 以 2.6.1 三条适配判据为准入门槛；不满足者作为**独立产品**而非本系统功能；见 2.6.3 |
| 领域概念渗回引擎 | 实现期顺手写 `if kind == "endpoint"` 或 `if doc_type == "详细设计"`，通用性在第二个文档类型到来时崩塌 | 引擎代码禁用词自动检索（NFR-28 / 验收 42）纳入 CI 门禁；新需求必须先尝试用投影规则表达 |
| 档案与模板包错配 | 档案引用的槽位在模板包中不存在（或反之），构建期才暴露 | 登记时校验档案 ↔ 模板包的双向引用；构建前做一次「档案可满足性」预检 |
| 子作业并发过度 | 子作业并行可能瞬间拉起 N 个构建，超出 worker 与模型服务承载 | 并发上限由服务端约束并在 P08 只读展示；同项目不同作业之间仍严格串行；见 4.8 |

## 附录 B 需求来源与设计独立性

**需求来源**：本设计的问题域与验收经验，来自一次真实的交付文档生产实践——需要在外部给定的、不可改动的 Word 模板约束下，把多种事实源（接口契约、数据模型、协议、需求、素材）组织成受文件编号体系管束的成套设计文档，并接受评审。

**适用范围声明**：该实践是**本设计的一个实例，不是本设计的范围**。设计文档只是 2.6.2 表中「软件交付类」的一行；本设计的目标是**与文档类型无关**（见 4.9）。任何把本设计读作「设计文档生成工具」的理解，都会低估其范围，也会误判 4.9 各条约束的必要性。

**独立性声明**（三条，用于避免把本设计误读为某个既有实现的改造方案）：

1. 该实践中产生的代码、脚本、模板与产物**不构成本设计的依赖**：不进入仓库、不参与验收判定、不作为实现参考；
2. 本设计**不存在「从旧实现迁移」的路径** —— 模块划分、依赖规则、数据模型与接口均按第 4 章重新定义，实现可自由选择最合适的做法；
3. 该实践的价值只体现在两处：**1.2 的问题清单**（需求来源）与 **4.3 的设计约束矩阵**（问题到约束的映射）。除此之外不作为设计依据。

另外，模板属于使用方的资产、交付文档属于项目机密，因此本设计的示例资产必须自制（见 10.10）。
